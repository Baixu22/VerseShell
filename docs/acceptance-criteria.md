## 0. 三条通用纪律
| # | 纪律 | 它挡住的失格写法 |
|---|------|-----------------|
| 1 | **预注册**：MDE／判定口径／最小样本量必须在**看到数据之前**写死。看到结果再调门槛 = 事后挑选 | 「我们把门槛从 0.7 调到 0.8 之后就通过了」 |
| 2 | **区间优先**：任何「更省／更快／更强」都必须给区间，并让**区间越过门槛那一侧**。只报点估计 = 不允许下结论 | 「D/A = 0.78，所以省了 22%」 |
| 3 | **区分「数据缺口」与「产品缺口」**：只有当**整个 CI95 都落在门槛的错误一侧**时，才允许说「加样本也救不回来」——那时必须写成产品缺口，禁止写成「还需要更多数据」。点估计越过门槛但区间仍跨到可达成的一侧，属于**无证据**：估计值会随样本移动，更多数据可能改变它 | 「再跑几轮就能证明 ≤0.6」；反过来，把「点估计 1.0074、区间 [0.82, 1.25]」说成产品缺口同样是失格 |

第 3 条是这份文件最重要的一条。机器判定见 `acceptance_power.json` 的 `gap_type` 与 `impossible_by_sample_size`：
两者都由**区间**导出，`impossible_by_sample_size` 只在 `CI95 下界 > 门槛（或点估计 cap）` 时为真。

> **2026-09-26 修订（TF-0099）**：原文写的是「点估计已在门槛错误一侧 ⇒ 产品缺口」。这条规则在统计上不成立
> ——点估计是随机变量，它越过门槛并不排除真值在门槛另一侧。复核（`docs/audit-r12-verification.md` §3.4、§4.1）
> 发现工具比 1.0074 `[0.8191, 1.2521]` 与 D/A′ token 比 1.0567 `[0.8435, 1.379]` 都被误判为产品缺口，
> 而两者的区间都明确包含 0.85 与 0.90 这类真值。已改为区间规则；同时修掉 `success_noninferiority_lower_bound`
> 的运算符优先级 bug（它此前报 +0.5864，真实的配对差值下界是 −0.0032）。

## 0.5 预算上限必须对三臂**都不构成约束**（控制效度硬要求）

任何「每次运行的预算上限」——`max_turns`（工具调用次数）与 `max_tokens`（单轮 completion）——都必须先证明它**没有在不对称地截断某一个臂**，否则比出来的不是接口差异，而是「谁的调用粒度更费预算」。

**实测反例（本轮）**：新任务集上跑 `max_turns=8` 时，

| 臂 | 撞上限比例 | 平均工具调用 |
|---|---|---|
| `raw_shell`（A） | **0/25 = 0%** | 3.04 |
| `raw_shell_coached`（A'） | 3/25 = 12% | 3.84 |
| `verseshell_aci`（D） | **16/25 = 64%** | 8.12 |

D 被截断 64%、A 一次都没被截断——**这个对比是被上限污染的**，D 的成功率与 token 都只是「被截断后的下界」。原因也清楚：typed op 粒度更细（`read_file` / `replace_in_file` / `run_command` 各算一次），而裸 shell 一条命令能读+改+跑。

**硬要求**：

1. 定版跑之前，先在小样本上量**三臂各自撞上限的比例**；任一侧 >10% 即视为上限构成约束，必须提高上限重跑。
2. 报告时必须给出**三臂的撞上限比例**，与成功率、token 比一起放；撞上限的行要能被单独排除后复算（`turns >= max_turns`）。
3. 这与 C13 的 `completion_truncated_turns` 是**同一类缺陷的两个实例**（一个是单轮输出预算，一个是整轮步数预算），处理方式相同：**让它可见、让它不约束、必要时重跑**。

> ### ⚠️ 「提高上限重跑」这条补救在本端点**不可用**（2026-09-27 实测）
>
> 第 13 轮重跑里 A′ 臂的 completion 截断率是 **16% / 12% / 12%（合计 13.3%）**，按上面的硬要求属于「上限构成约束」。
> 但在花 3.5 小时重跑整臂之前，我们先做了一个廉价探测（`audit-r12-scratch/probe_cap_raise.py`）：
> 把那 11 个被截断的单元格**用 `--max-tokens 32768` 原样重跑一遍**，只改预算。
>
> | 结果 | 个数 |
> |---|---|
> | 通过 | **2 / 11** |
> | **仍因长度截断** | **0 / 11** |
> | **HTTP 502「非流式响应超时(300秒)」** | **9 / 11** |
>
> 失败墙钟全部聚在 **~300 秒**（302/304/306/308/312s）。也就是说：
>
> - **16384**：模型在难任务上把预算烧在 reasoning 上 → `finish_reason=length` → 该轮不发工具调用 → 记成普通失败；
> - **32768**：同一个单元格的生成时间越过 proxy 的 **300 秒非流式响应上限** → **HTTP 502** → runner 记成 `api_error` 行，
>   而 `merge_live_runs.py` **遇到任何 `api_error` 行就拒绝合并**（exit 2）。
>
> **所以抬高上限并没有让这一轮变干净，只是把「长度截断」换成了「api_error」。**
> 端点的 300 秒上限与「推理模型会把 completion 预算烧在 reasoning 上」这两件事合起来，
> **把可达的 completion 预算锁死在约（300 秒 × 生成速率）**——本端点上大约两万 token 量级，没有安全余量。
>
> **推论（已登记为 requirement 节点）**：
> 1. §0.5 的第 1 条**不能**当作总能执行的补救；遇到本端点这类硬上限时，正确做法是
>    **预先写死「截断行/端点失败行如何处置」的规则**（tree-farm `TF-0118`），而不是反复重跑。
> 2. **截断不是随机分布的**：11 个单元格里有 10 个集中在 **4 个任务**上
>    （`python_config_reader_686653a1`、`rust_window_fold_scanner_3d213f38`、
>    `typescript_missing_await_result_order_c58cafb6`、`typescript_reduce_shared_accumulator_d80f462d`），
>    且每个 seed 都复现。**这些恰是较难的任务**——所以「排除截断行」会顺带把难任务排除掉，
>    那会改变构造效度，不能当作无代价的清理。
> 3. 同一份配置的截断率在三次独立运行之间是 **15% → 7% → 13.3%**。
>    **「这一轮预算没构成约束」很可能是运气，而不是配置的性质。**

**第二次实测（`max_turns=20`，同一任务集）**：A/A' 已降到 **0%**，但 **D 仍撞 20%**（13.04 次调用 vs A 的 5.24）。更关键的是**排除撞上限的行会翻转结论**：

| 口径 | D/A 观察 token 比 | CI95 |
|---|---|---|
| 全部行 | **1.1398**（D 更贵） | [0.8206, 1.611] |
| 排除撞上限行（丢 5 行） | **0.8617**（D 更省） | [0.615, 1.329] |

**符号被上限翻转了**——这正是 §0.5 存在的理由。工具 `tools/three_arm_report.py` 把这个判定自动化：它逐臂报告撞上限比例、给出 `cap_ok` 与一句话判决，并把「全部行」与「排除撞上限行」两个口径并排输出。

**判定自动化**：`python tools/three_arm_report.py --out eval/three_arm_report.json` → `cap_ok: false` 即表示**当前 run 不可作为定版**。

### 0.5.1 预算**不是**中立参数（第三次实测，这条推翻了「抬高上限即可」的想法）

把上限从 20 抬到 40 之后，**截断从 D 转移到了 A**，而且两臂的调用数都变了：

| `max_turns` | A 撞上限 | D 撞上限 | A 工具调用 | D 工具调用 | 单格耗时 |
|---|---|---|---|---|---|
| 8 | 0% | **64%** | 3.04 | 8.12 | ~26s |
| 20 | 0% | **20%** | 5.24 | 13.04 | ~45s |
| 40 | **12%** | 8% | **9.96** | 14.92 | **66s（最长 546s）** |

**模型会扩张到把给它的预算用掉。** 给 40 步，A 就从 5.24 涨到 9.96，并出现「40 步全部用完然后失败」的 run（单格 546 秒 = 9 分钟）。

所以：

- **「把上限抬到不构成约束」在原理上达不到**——抬高上限会同时改变两臂行为，它不是一个中立旋钮；
- 只能**固定一个预注册的上限**，然后**同时报告**：三臂截断率、全部行口径、排除截断行口径；
- 并且要报告**单格耗时分布**——上限过高会让 run 退化成「烧完预算」，既慢又测不到能力。
- **补充（2026-10-03）**：以上假设「抬得够高总能脱绑」，但 `step-5-preview` 证明存在
  **抬预算完全不脱绑的"循环型"模型**（mt=20 → mt=40：平均轮次 11.95 → 19.80，而撞上限
  **格数 34 → 34 一格未减**，成功率反而 0.7333 → 0.6571）。判别与处置见 §0.5.4 末节。

**取值**：`max_turns=20`（第 11 轮实测 A/A' 0% 截断、D 20%；**r15-2026-09-29 实测 A 1/105、A′ 3/105、D 0/105，没有任何一臂构成 cap 约束**），并在报告中把 D 的截断率与其影响一并给出。**D 需要更多步数本身就是 ACI 调用粒度的真实代价**，不是纯粹的测量噪声——但它同时意味着 D 的数字是**下界**，两者都要写清楚。

### 0.5.2 「预算敏感」任务清单与其判定方式（tree-farm TF-0120）

**为什么需要一条清单**：截断**不是随机分布**的。第 13 轮 11 个被截断单元格里 **10 个集中在 4 个任务**上，且每个 seed 都复现；
所以「这一轮预算没构成约束」可能只是因为抽到的任务组合比较温和。**任务设计必须建立在本端点的硬上限之上，而不是假设总能抬预算。**

**判定方式（机检，不看结论）**

| 判据 | 阈值 |
|---|---|
| 该任务在某臂上的 `completion_truncated_turns > 0` 的行占比 | 任一臂 **≥ 10%** 即标记为**预算敏感** |
| 该任务的裸 shell pristine 观察 token | 仅作背景；与截断的因果关系未证实，不参与本条标记 |
| 判定只看产物字段（`completion_truncated_turns`、`turns`、`observation_tokens`），**不看该任务是成功还是失败** | — |

**历史预算敏感任务示例**（第 12/13 轮；不是当前自动判定名单）：
`python_config_reader_686653a1`、`rust_window_fold_scanner_3d213f38`、
`typescript_missing_await_result_order_c58cafb6`、`typescript_reduce_shared_accumulator_d80f462d`。

**登记位置（重要）**：清单**不写进 `bench/aci/tasks/*.json`**。原因是那些文件在 live 证据的指纹覆盖面内——
在第 14 轮 live 正在跑的时候改动它们会让刚产出的产物**立刻被判陈旧**，属于自伤。
清单作为**派生判定**写入 `eval/budget_sensitivity.json`，由 `python tools/budget_sensitivity.py`
从当前 with/without 两份结果重新计算，并接入重刷链及 C12 新鲜度检查。按数据臂、模型、
条件、任务分别统计全部已观测行；`budget_sensitive_completion` 用
`completion_truncated_rows * 10 >= rows`，`budget_sensitive_turn` 用
`turn_capped_rows * 10 >= rows`，`budget_sensitive_any` 是两轴的并集。为兼容旧消费者，
`budget_sensitive` 字段仍只代表 completion 轴，不得拿它当两轴完整标签。
不能用四舍五入后的比例，也不能跨臂稀释；成功与否、端点错误和观察大小不参与判据。
缺失 `completion_truncated_turns`、`turns` 或 `live_config.max_turns` 时直接报错，
不输出“无敏感任务”。

本节的逐任务 **≥10%** 诊断不等于 §0.6 的逐臂 **>10%** 排除判据。主张资格仍由
§0.6 的逐臂比例、方向一致和零 API 错误规则决定，两个口径仍须并排报告；此清单不
新增任何豁免或拒绝门槛，不用于删除任务，也不证明提示长度、任务难度或端点超时的因果关系。

**禁止**

- ✗ 为了绕开上限而删除难任务（那些任务恰是较难的，删掉会改变构造效度，见 §0.6.5）。
- ✗ 把 `HTTP 502` 当成模型失败计入成功率（它会让 `merge_live_runs.py` 拒绝产物，必须先修端点侧）。
- ✗ 在预注册之外新增「预算敏感」豁免来让某条结论可主张。

**覆盖面（2026-10-10 更新）**：`tools/budget_sensitivity.py` 现已同时派生
completion 与轮次两轴：`completion_truncated_turns` 覆盖单轮 completion 预算，
`turns >= live_config.max_turns` 覆盖轮次预算，`budget_sensitive_any` 给出两轴并集。
旧字段 `budget_sensitive` / `sensitive_task_ids` 保持不变，仍只表示 completion 轴，
避免静默改变历史消费者语义。

- `tools/three_arm_report.py` 仍是**逐臂**判定（`cap_ok` / 三臂撞上限率），用于判断
  「这一轮有没有被预算污染」；它不是逐任务清单，两个口径不可互相代替。
- `tools/task_admissibility.py` 会把 `eval/budget_sensitivity.json` 的两轴标签作为
  informational `budget_sensitivity` 字段附在候选准入记录上；它**不改变**准入判定，
  缺失或不可读的标签记为 `not_measured`，不能当作 not sensitive。
- 本清单是观测诊断，不新增豁免、不删除任务，也不证明提示长度、任务难度或端点超时的因果关系。

### 0.5.4 第四、五次实测：混淆的**方向与幅度都是模型依赖的**（2026-10-03，4 个模型的预算曲线）

前三次实测（§0.5 / §0.5.1）都在同一模型上，观测到「`max_turns=8` 时 **D 被截断 64%**，抬高上限后截断
**转移**到 A」。在一个完全不同的模型上重做三点曲线，得到**相反的初始分布**：

| `max_turns` | A `raw_shell` | A′ `raw_shell_coached` | D `verseshell_aci` | A 成功率 | A′ 成功率 | D 成功率 |
|---|---|---|---|---|---|---|
| 8 | **27.7%** | **34.0%** | 2.1% | 0.6809 | 0.7447 | 0.9787 |
| 20 | **21.0%** | **16.2%** | 0.0% | 0.7619 | 0.8000 | 1.0000 |
| 40 | 8.6% | **10.5%** | 0.0% | 0.8952 | 0.8762 | 1.0000 |
| **80** | **4.8%** | **0.0%** | **0.0%** | **0.9238** | 0.9048 | 1.0000 |

（hy3，本地 OpenAI 兼容 relay，task set 3.1.0，seeds 42/43/44；
**mt=8 行只有 seeds 42/43**——该轮被外部终止，产物按 §0.6.7 视为 partial，只作方向证据。
**mt=80 是 hy3 上第一份通过 §0.5 的产物**：`tools/three_arm_report.py` 判
`no arm exceeds the cap-binding limit on either budget`，两个对比均 `claimable=True`
（排除率 A 5.7% / A′ 1.9% / D 0.0%），产物
`bench/aci/results/c16-hy3-mt80-20261003/latest_live.json`，`api_error_rows=0`。
mt=20 与 mt=40 仍判 `cap_ok: false`——mt=40 的阻塞原因是 A′ 10.5% 与两臂 11.4% 排除率。
**注意：达标所需预算本身是模型属性**，不能把 mt=80 当成本任务的通用取值。）

**这次被截断的是 A/A′，不是 D。** ACI 臂在三个预算上撞上限率都 ≤2.1%，shell 两臂最高到 34%。
所以 §0.5 那句「typed op 粒度更细，所以 D 更费预算」**不是普遍规律，而是模型依赖的**：
粒度更细并不必然意味着调用次数更多——本模型在 shell 下会反复试错（mt=8 时 A 5.66 次 / A′ 6.00 次
vs D 4.70 次）。

**由此，混淆的偏袒方向也不同：本模型上偏袒 D。** 随预算上升：

| `max_turns` | D−A 成功率（ITT 口径） | D−A 成功率（可分析口径） |
|---|---|---|
| 8 | **+29.8pp** | 预算绑死，该口径不成立 |
| 20 | +23.8pp | **+3.7pp** |
| 40 | +10.5pp | **+3.2pp** |

**ITT 口径随预算掉到约 1/3，可分析口径稳定在 ~3pp。** mt=8 那类「D 领先近 30 个百分点」主要是
排除率造出来的，不是能力差异；预算充足后真实优势约 **+3pp**。这与 §0.5.1「上限不是中立旋钮」
互为独立证据，但把它的**方向**补上了：早先记录的是「截断 D → 偏袒 A」，本模型是「截断 A → 偏袒 D」。

**第二个反转**：mt=8/20 下 A′（提示词等量对照）高于 A，符合 §4.1 的对照设计预期；但 mt=40 下
**A′（0.8762）低于 A（0.8952）**。即「提示词匹配」在预算充足时不再带来增益，说明 A′ 先前的优势里
也含预算成分。引用 C1 的对照臂结论时必须同时说明预算。

**真实计费口径同样随预算漂移**（固定模型、只改预算）：

| `max_turns` | D/A usage 比值（ratio-of-means） | D/A usage 比值（mean-of-ratios） | D 逐对更贵的比例 |
|---|---|---|---|
| 8 | 1.227 | 1.820 | 34/47 = 72% |
| 20 | 0.456 | 1.657 | 68/105 = 65% |
| 40 | 0.335 | 1.575 | 66/105 = 63% |

**总账口径漂 4 倍且方向翻转，逐任务口径稳定在 1.58–1.82。** 所以「D 省 token」只在
「总账口径 + 特定预算」下成立；逐任务口径下无论预算多少，D 都在约 2/3 的任务上更贵。
这与 §1.5 的口径纪律一致：两个估计量必须并排报告，不得挑一个当结论。

**对 §0.5 的修订**：

1. 「抬高上限即可解决」已被 §0.5.1 否定；本条补充：**混淆的方向也依赖模型**。因此
   「预期哪一个臂会被截断」**不能写死在预注册里**，只能每轮实测后照实报告。
2. §0.5 的三条硬要求不变（量撞上限比例、与成功率/token 并排、可排除后复算）。
3. 预算不足时，**可分析口径**（排除被截断行）比 ITT 稳定得多，应作为主口径；ITT 的数值对
   排除率极其敏感（本轮两者相差 6.8 倍：+0.0323 vs +0.1429）。

**跨模型复现（2026-10-03，第 4 个模型加入后）**：同一现象在**四个模型**上独立成立，
且**高预算下的效应量收敛**：

| 模型 | 预算点 | 脱绑所需 `max_turns` | D−A 成功率差（ITT） | 排除率（A/A′/D） | REAL(mor) |
|---|---|---|---|---|---|
| hy3 | 8 / 20 / 40 / **80** | **80** | +29.8 → +23.8 → +10.5 → **+7.6pp** | 27.7 / 34.0 / 2.1 → **5.7 / 1.9 / 0.0**% | 1.82 → **1.51** |
| deepseek-v4.1-flash | 20 | 20 | **+7.6pp** | 6.7 / 3.8 / 0.0% | 1.91 |
| glm-5.3-flash | 8 | >8（未满足） | +14.6pp | 7.8 / 11.7 / 3.8% | 2.25 |
| **step-5-preview** | 8 / 20 / **40** | **无论多高都不脱绑** | +38.1 → +23.8 → **+34.3pp** | 63.8 / 62.5 / 21.0 → **32.4 / 21.9 / 1.9%** | 1.37 → 1.24 → 1.27 |

（`D−A 成功率差` 一列用**任务配对**口径，与 §0.6.2 的"可分析口径"不同；`step-5-preview`
mt=40 的配对值为 +0.3429。该列只用于**同一模型跨预算**的趋势比较，不用于跨模型比较，因为
各模型的脱绑程度不同。`REAL(mor)` 是逐任务真实计费 token 比值的均值。）

**三条结论**：

- **低预算制造出的"优势"在四个模型上都虚高**（+14.6 / +29.8 / +38.1pp），而**两个已脱绑的
  模型收敛到同一量级（+7.6pp）** —— 不同模型、不同端点（本地 relay 与 StepFun 公网 API），
  效应量几乎重合。这支持「预算混淆的方向与幅度是系统性的」，不是单一模型的偶然。
- **→ "D 省 token" 在所有配置点上方向一致地不成立**：`REAL(mor)`（逐任务口径）落在
  **1.24–2.25**，即无论模型、无论预算，D 都在多数任务上真实更贵；而 `REAL(rom)`（总账口径）
  在 0.12–1.53 之间漂移并跨 1.0。§1.5 要求两个估计量并排报告，本条即是理由。
- **最强的单点演示是 `step-5-preview` mt=8**：排除率 **63.8%**，可分析口径
  **succ_an = +0.0000**（排除后两臂打平）而 ITT 口径 **succ_itt = +0.4286**——
  **同一份数据，两个口径差 42.9 个百分点**。该点 `claimable=False`（§0.6.3 自动拦截），
  **不得**作为任何结论的证据，只作混淆机制的演示。

**新类型：抬预算**无效**的模型（2026-10-03，`step-5-preview` mt=20 → mt=40）**

§0.5.1 只说「抬高上限会同时改变两臂行为」，隐含假设「抬得够高总能脱绑」。`step-5-preview`
推翻了这个假设：

| | mt=20 | mt=40 | 变化 |
|---|---|---|---|
| A 臂平均轮次 | 11.95 | **19.80** | +66%（把新预算全部用掉） |
| A 臂**成功格**平均轮次 | 9.03 | **10.28** | +14%（更多预算没换来收敛） |
| A 臂撞上限**格数** | 34 | **34** | **一格未减** |
| A′ 撞上限格数 | 24 | 22 | 几乎不变 |
| A 臂成功率 | 0.7333 | **0.6571** | **反而下降** |

**预算翻倍，撞上限的格子一个都没减少。** 所以这批失败与预算无关——模型在这些任务上会持续
循环，给多少用多少。同一模型的两个预算点是**独立测量**（`api_error_rows=0`、`partial=False`、
315 行完整），排除了"数据缺失"这一解释。

**推论（对 §0.5 补救条款的再次限制）**：

1. **§0.5 的「抬上限重跑」只对"预算受限型"模型有效。** 判别方法廉价：先跑 `max_turns=8`，
   若 shell 臂撞上限率 **>30%**，再抬到 20 看撞上限**格数**（不是比率）是否下降；
   **不降即为"循环型"，此模型在这套任务上无法通过 §0.5**，继续抬预算只是烧时间。
2. **不要用比率判断收敛**，要用**格数**。step5 的比率从 32.4% 微降到 32.4%（同一批 34 格），
   因为分母没变；若只看比率容易误判为"在改善"。
3. **成功率可能随预算上升而下降**（0.7333 → 0.6571）。更多轮次会把"提前放弃"的格子
   变成"耗尽预算后失败"，所以**"抬预算至少不会更差"这个直觉不成立**。
4. 该模型仍可用于**可分析口径的诊断**（D 的 token 优势在那里依然显著），但**不得**用于
   任何 §0.6.3 意义上的可主张成功率对比。

**对「ACI 臂不吃预算」的修订**：`step-5-preview` 的 ACI 臂在 mt=8 时撞上限 21.0%，但随预算
上升迅速收敛（mt=20 3.8%、mt=40 1.9%），而**同轮次的 shell 臂始终停在 32%/21%**。
所以原先「ACI 臂也大量撞上限」的观察**只是低预算下的暂时现象**，不是该模型的固有属性；
「D 被截断得少」这一条在四个模型上**都成立**，前提是预算足以让该臂脱绑。

## 0.6 行处置规则（**预注册**，2026-09-27 / tree-farm TF-0118）

> **为什么需要这条**：§0.5 的补救是「撞上限就抬上限重跑」，但 2026-09-27 的实测证明**本端点做不到**——
> 11 个被截断单元格改用 `max_tokens=32768` 重跑后，**0 个仍长度截断、9 个变成 HTTP 502**（proxy 300 秒非流式上限），
> 而 502 会让 `merge_live_runs.py` 直接拒绝合并（见 §0.5 上方的实测块）。
> **既然无法靠抬上限消除截断，就必须事先写死每类行怎么处置**——否则「用哪一套行」会变成看到结果之后才做的决定，
> 那正是 `docs/audit-brief.md` §6 P7 与 §3.1 纪律 1 都要防的分叉花园。

### 0.6.1 行的分类（只看产物字段，不看结论）

| 类别 | 判定（全部来自产物字段） | 性质 |
|---|---|---|
| `endpoint_failure` | 该行有 `api_error`，或 `harness_crash` / `harness_fault` 为真 | **环境失败**，与模型能力、与臂都无关 |
| `cap_truncated` | `completion_truncated_turns > 0` **或** `turns >= max_turns` | **预算受限**：该轮没得到行动的机会 |
| `analysable` | 以上都不是 | 头条可用 |

### 0.6.2 两个口径**必须同时报告**

1. **`analysable`（主口径）**：只用 `analysable` 行。
2. **`intention_to_treat`（ITT，必报）**：全部行，把 `endpoint_failure` 与 `cap_truncated` 记作**失败**。

**两个口径的数字必须并排出现在同一张表里，不允许只报其中一个。**

### 0.6.3 一条对比要可主张，必须**同时**满足三条

1. 该对比的**两个臂**各自：`endpoint_failure` 比例 ≤ 10% **且** `cap_truncated` 比例 ≤ 10%；
2. 两个口径**方向一致**（相对于该项门槛，都落在同一侧）；
3. `api_error` 行数为 0（否则合并脚本本来就拒绝产物）。

任一条不满足 → **该对比不可主张**，只能引用 ITT 口径并标注「受预算/环境约束，方向可能被假象支配」。

> **为什么按「对比」而不是按「整轮」判定**：截断是**单侧**的。第 13 轮重跑里只有 A′ 被截断 13.3%（A 1%、D 0%），
> 按整轮一刀切会把不受影响的 **D vs A** 一起作废。而 §0.5 的原话是「**任一侧**撞上限 >10%」——
> 「侧」指的就是**这个对比的一侧**，不是整轮。

### 0.6.4 不做的事

- **不按臂、不按任务选择性排除**：同一类别对所有臂、所有任务一视同仁。
- **不用排除来「修好」结论**：如果一条结论只在排除后才成立，§0.6.3 的第 2 条会挡住它。
- **不隐藏被排除的行**：每类行的逐臂计数与比例都必须在产物里（`eval/three_arm_report.json` 的 `row_policy`）。

### 0.6.5 已知的构造代价（**必须与结论一起说**）

剔除 `cap_truncated` 会顺带剔除**较难的任务**——实测 11 个被截断单元格里有 **10 个落在 4 个较难任务**上
（`python_config_reader_686653a1`、`rust_window_fold_scanner_3d213f38`、
`typescript_missing_await_result_order_c58cafb6`、`typescript_reduce_shared_accumulator_d80f462d`），且每个 seed 都复现。
所以**主口径实际估计的是「较易子集上的效应」**。引用主口径的结论时，**必须同时给出被剔除任务的比例**。

### 0.6.6 落到代码上的位置

| 位置 | 做什么 |
|---|---|
| `tools/live_uncertainty.py::row_policy()` | 唯一的分类实现（两个工具共用，避免各写一套） |
| `tools/live_uncertainty.py::row_budget_axis()` | §0.6.8 的逐轴分解 `completion_cap` / `turn_cap` / `repeat_call_cap`（**诊断**；门禁仍用 `row_class()` 的**并集**） |
| `tools/three_arm_report.py` | 输出逐臂 `row_policy`、两个口径的成功率、逐对比的 `budget_ok` 与 `sign_agreement` |
| `tools/acceptance_power.py` | 每个对比块带 `row_policy`；**未通过 §0.6.3 的对比，其 `claimable` 一律为 false**，并给出 `policy_blocked` 原因 |
| `tools/claim_gate.py` **C33** | 机检一致性：**只要某个对比的 `budget_ok` 为 false，该块里就不得存在 `claimable=true`**；且两个口径必须都出现在产物里 |

### 0.6.7 Partial 合并只保存诊断，不授予主张资格（P1-1）

默认合并仍拒绝 endpoint_failure（含 api_error）。测试方显式使用 --allow-api-errors
时，输出带 partial: true，所有行由同一 row_class() 分类；原始失败行不会被丢弃。
端点失败行的 success 记为 null，原值保存在 raw_success，避免在普通已验证成功率中
把环境失败当成模型失败。没有任何已验证行的条件，其成功率为 null。

这不改变 §0.6.2 的 ITT 定义：保守 ITT 仍把排除行计作失败，并与 analysable 主口径
并列报告。合并产物的普通聚合只是不把未知状态算成已验证失败，不能冒充 analysable
主口径；partial 中的数值只作诊断，所有合并对比的 meets_acceptance / claimable 为 false。

--allow-api-errors 即使没有错误行也会保留显式 partial 标记；再次合并已有 partial
输入也不能自动去掉标记。要得到完整产物，必须从补跑后确认完整、无错误的原始运行
重新按默认严格模式合并，不得只改标记或删掉失败行。

补跑工具 splice_live_cells.py 只接受记录了预算等配置的原始运行文件，拒绝 merged_from
输入；逐格使用原 max_tokens、max_turns、seed 等设置。每个非端点失败的结果（包括真正
的模型任务失败）立即原子落盘。原始运行经过实际补跑且 endpoint_failure 清零时，
可从该运行的当前行派生 partial=False；这不是通过重新合并或手改标签来清除 partial。

C35 的零 api_error 要求保持不变，并拒绝 partial 或错误的逐行分类；它从原始字段
重新分类，列出受影响的 task_id、condition、seed、source_run、run_index 和对比。
因此“允许保存 partial”不等于“允许 partial 通过门禁”。未改 C14/C16 或任何比例阈值。

### 0.6.8 双预算 × 双口径的截断比较（**预注册**，2026-10-10 / tree-farm TF-0121）

> **为什么需要这条**：第 14 轮 D 臂独有 **15/105 格** completion 截断（14.3%），
> 全量口径 D−A = **−6.7pp**、剔除截断行后 **+1.6pp**，**符号翻转**
> （C13、`docs/repair-handoff-2026-09-29.md` §P0-1）。§0.6.1 把两类预算合并成一个
> `cap_truncated`，无法回答「是**哪一种**预算把这一格截掉的」，也就无法在下一轮之前
> 定死缓解目标。本条把**两个预算轴 × 两个口径**写死，同时**不放宽** §0.6.3。

**术语（只看产物字段）**

| 轴 | 冻结来源 | 触发它的行字段 |
|---|---|---|
| `turn_cap`（轮次预算） | `live_config.max_turns` | `turns >= max_turns`；`stop_reason == "turn_limit"` 仅作补充（合并产物可能不带 `stop_reason`） |
| `completion_cap`（单轮 completion 预算） | `live_config.max_tokens` | `completion_truncated_turns > 0` |
| `repeat_call_cap`（重复调用策略） | `live_config.repeat_call_limit` | `stop_reason == "repeat_call_limit"` |

两个口径沿用 §0.6.2：`analysable`（主口径）与 `intention_to_treat`（ITT，必报）。

**分类（单一实现，字段驱动）**

`tools/live_uncertainty.py::row_budget_axis()` 返回该行命中的轴集合，`row_class()` 由它导出：
`endpoint_failure` 优先（§0.6.1 的字段集不变）；否则任一轴命中即为 `cap_truncated`；否则 `analysable`。
一行可以同时命中多个轴（例如既撞轮次又发生 completion 截断）：**每个轴各计一次，并集只计一次**。

**报告矩阵（每个变体、每个对照单独一行）**

- 逐臂 × 逐轴 × 逐口径：`n`、`endpoint_failure`、`completion_cap`、`turn_cap`、`repeat_call_cap`、
  多轴重叠数、并集 `cap_truncated`、`analysable` 与 ITT 成功率，并给逐轴比率。
- 逐对照（如 D−A、D−A′）：**两侧**的同一份分解；**不得跨变体（baseline/compact_all）合并**，
  不得只报并集，也不得只报一个口径。
- `completion_cap` 另附 `tools/live_turn_diagnostics.py` 的子类分布（`reasoning_burn` /
  `budget_burn_without_reasoning_evidence` / `truncated_other_turn` / `unknown_*`）。该分布是**标注**，
  不是排除；`unknown_*` 永远不读作 `no_truncation`。

**门禁（不放松）**

一条对比可主张，仍须**同时**满足 §0.6.3 全部三条：两臂 `endpoint_failure ≤ 10%` 且**并集**
`cap_truncated ≤ 10%`；两个口径方向一致；`api_error == 0`（另含 §0.6.3 的重复调用一致性检查）。

- 双预算分解**只用于说明与归因**：并集超 10% 即不可主张，**不得**因「只有 completion 这一轴超标」
  或「另一轴干净」而改判。并集 ≤ 10% 必然蕴含每个轴 ≤ 10%；若改用逐轴门槛替代并集，反而允许高达 20%，
  属于放宽，禁止。
- `completion_cap` 的子类（含 turn-1 零工具调用）**不改变可主张性**。任何按子类做排除或敏感性分析的做法，
  必须作为**独立的、在采集前冻结的编号敏感性分析**登记，并与主口径并列，不得事后决定。

## 0.7 假设族与多重比较（**预注册**，2026-09-28 / tree-farm TF-0113）

> **问题**：`eval/acceptance_power.json` 一次判 **11 项**，每项各自用 α=0.05。这在**单项**上没错，
> 但在**族**上不是 5%：11 项独立时族错误率 = `1 − 0.95¹¹ = 43.1%`。
> 贴边界的可主张项（例如 D/A′ 观察 token 上界 0.9788、余量仅 0.0212）**经不起这个校正**，
> 所以「可主张」这三个字在多项并报时必须先做族错误率控制。

**分组（预注册，不得在看到数据后移动）**

| 族 | 成员 | 校正 |
|---|---|---|
| `live_model` | 成功率 D/A、成功率 D/A′、token 比值 L1/L2/冻结目标、工具比 L1、CPST D/A、CPST D/A′（共 9 项） | **Holm-Bonferroni**，α=0.05 |
| `cross_shell` | 跨 shell「每操作严格更快」、「每操作 ≥2 倍」（共 2 项） | **Holm-Bonferroni**，α=0.05 |
| `exploratory` | **不在上两张表里的一切**（事后新增、无预注册门槛） | 无门槛；**永远不得作为确认性结论引用** |

**分组依据是数据来源与问题，不是方便**：跨 shell 的两项来自本地进程基准、有自己的预注册与数据集，
因此与 live 模型那一梯**不共用一个校正**——混在一起会让两边都失去意义。

**判定规则**

1. 每个判定必须声明 `family`（`tools/acceptance_power.py` 的 `VERDICT_FAMILIES`）。
2. 确认性族内用 **Holm** 逐步法：把族内 p 值升序排列，第 i 个与 `α/(m−i+1)` 比较，一旦某项不通过则其后全部不通过。
3. `claimable` 只在**同时**通过区间门槛（§4.3）与 Holm 之后才为真；原值保留在 `claimable_before_multiplicity`。
4. `exploratory` 判定的 `claimable` **一律为 false**，且必须能被门禁检出。

**口径诚实性（必须与数字一起说）**

- 判定是**区间式**而非 p 值式，所以 Holm 需要一个 p 值来源：由该判定自己的
  `(point, ci95_lower, ci95_upper)` 反推 `SE ≈ (upper − lower) / (2·z₀.₀₂₅)`、`z = (threshold − point)/SE`。
  产物里标为 **`p_value_kind = "approx_from_ci95"`**——它只是让校正**能**做，**不替代**区间规则。
- **成功率两项是设计/功效判定**（问「n 够不够检出预注册 MDE」），不是显著性判定，因此
  `passes_holm = null`，不参与 Holm。这条限制**照实报告**，不许当成"已校正"。
- 跨 shell 两项的评分三元组取**区间最宽的那个操作**（它是唯一可能让「每操作都成立」失败的操作）；
  没有它，该族会显示 `corrected: true` 而实际什么都没校正。

**落到代码上**

| 位置 | 做什么 |
|---|---|
| `tools/acceptance_power.py::VERDICT_FAMILIES` | 预注册的分组表（唯一事实来源） |
| `tools/acceptance_power.py::apply_multiplicity()` | 打 `family` 标签、按族做 Holm、写 `multiplicity` 块（含 `demoted_by_multiplicity`） |
| `tools/claim_gate.py` **C36** | 机检：每个判定都必须有 `family`；`exploratory` 不得 claimable；claimable 不得 `passes_holm=false`；被降级项不得仍 claimable |

## 1. 验收区 A：真实解决问题的能力（成功率）

**测什么**：同一批任务上，D（ACI）相对 A（裸 shell）的**成功率差**。

**对照设计（硬要求）**

1. **同模型、同任务集版本、同 seed、同 `max_turns`／`max_tokens`／`temperature`**，只有接口不同。任何一项不同即`不可比`，必须重跑。
2. **配对**：判定单位是 `(task_id, seed, run_index)`；A 与 D 必须成对存在，用 **McNemar**，不用独立两样本 z 检验（后者在本设计下是错的检验）。
3. **A 侧提示词必须"尽力"**：A 侧不能是稻草人。若 A 只拿到裸工具而 D 拿到精心写的 ACI 规则，那比出来的是提示词工程，不是接口——见第 4 节 C1 对照臂。
4. **成功谓词必须是行为判定**，且满足：pristine 失败 / GOLDEN 通过 / **写法不同的等价修复也通过**（已由 C24 机器化，10/10）。
5. `unverified`（判定跑不起来，返回 `None`）的行**不得计入分母**；若 `unverified_rows > 0`，成功率必须写成区间。

**样本量门槛（预注册 MDE = 0.15 绝对差，α=0.05 双侧，power=0.80）**

- 需要的配对数由**试点不一致率 ψ**决定：`n = [z_{α/2}·√ψ + z_β·√(ψ−δ²)]² / δ²`
- 当前试点 ψ = 0.1333（30 对里 4 对不一致）→ **需要 45 对**（10 任务 × 5 seeds）
- **当前 30 对 → 样本不足**。在 30 对下，只有 `|Δ| ≥ 0.187` 才能被检出；观测到的 `|Δ| = 0.067` **远在检出限之下**，所以「D 成功率更高/更低」本轮**两头都不能主张**
- 引用时必须同时给出**当前 n 的检出限**，不能只给 p 值

**判定规则（全部满足才可主张"成功率有差异"）**

1. `n_pairs >= n_required`（本 MDE 下 45）
2. McNemar 双侧 `p < 0.05`
3. 配对差 `D − A` 的 **CI95 不跨 0**
4. 观测效应量 `>= 预注册 MDE`。若小于 MDE，**只能写"未检出差异"，不得写"有差异但很小"**

**禁止的写法**

- ✗「D 成功率明显高于 A（+0.167）」← 未给区间、未给检出限、未预注册
- ✓「n=30 对时检出限为 |Δ|≥0.187，观测 |Δ|=0.067，未检出差异」

## 2. 验收区 B：与 PowerShell / Git Bash 的真实差距

**测什么**：同一台机器上，VerseShell 与 PowerShell 5.1 / Git Bash 做**同一件事**的墙钟差距。

**对照设计（硬要求）**

1. **等价性先证明，再比时间**：每个操作必须声明"各 shell 的最廉价等价命令"，且**输出等价**（归一化后比对，不能只看退出码 0）。等价性不成立的对比直接作废。
2. **同样的工作量**：负载对齐（例如 `range(1,1001)` 必须真的产生 1000 个元素）。
3. **交错执行**，不要一个 shell 连跑 20 次再换下一个——那会把热降频/后台负载算成 shell 差异。
4. **预热丢弃**（≥3 次），每次都是真实进程 spawn，stdout/stderr 一律丢弃。
5. **配对到迭代**，报告**中位数**而不是均值（墙钟右偏）。
6. **headline 取最差操作**，永远不要把最快的那个操作当结论。

**样本量门槛**：每个操作每个 shell ≥20 次迭代，且比值必须给 **bootstrap CI95**。

**判定规则**

| 级别 | 门槛 | 当前 |
|---|---|---|
| 「严格更快」 | 每个操作 `CI95 上界 < 1.00` | ✅ 5/5 |
| 「快 2 倍」 | 每个操作 `CI95 上界 < 0.50` | ✅ 5/5（最差 CPU info：点估计 0.2535，CI95 [0.2424, 0.2704]） |

**失效边界**：单机、单次会话、含进程启动开销；不代表别的 CPU/OS/工具链；不测吞吐/内存/并发。

**禁止的写法**

- ✗「平均快 15 倍」（把 32× 和 3.9× 平均）← 必须写最差操作
- ✗「PowerShell 慢 100 倍」（拿非等价命令比）

### 4.2 口径：必须用真实 tokenizer，且给出代理误差

本仓库的观察 token 是代理量 `observation_tokens = max(1, len(text)//4)`，只对**交付给模型的观察文本**计数：它**不是**端点输入 usage，也**不是**花费。

**当前实测（`eval/token_proxy_calibration.json`，`generated_at` 2026-09-29T07:55:06+08:00 = UTC 2026-09-28，`method_revision=2`）**：`real/proxy` 均值 **1.2442**、中位 **1.2150**（sd 0.2268，范围 [0.7361, 1.7451]）；**52/60** 样本代理**低估**、**7/60** 代理**高估**、**1** 相等；按字符类别 ASCII-only n=**47** 均值 **1.2505**、非 ASCII（`non_ascii_other`）n=**13** 均值 **1.2213**。锚点通过：400 字符英文段落 = 100 proxy vs 89 real（预期 [80,120]）。形状面板给出具体反例：**CJK 段落 278 字符 / 284 real token**（比 4.1159），即代理**并不被字符数上界住**。

> ⚠️ **P2-5 口径修复 caveat（全文测量 bug，2026-09-29）**：上一段的数字来自**修复前**的 `eval/token_proxy_calibration.json`。修复前，每个样本的 `real_tokens` 是在**产物内截断过的文本副本**上算的，而 `chars` / `char_class` 描述的是全文（60 个样本中 **6 个**受影响），所以那个 aggregate 混了两种文本。修复后所有指标都在全文上测量（并记录 `utf8_bytes` 与 `measurement_integrity`）；按修复后代码做的**离线重算**为：`real/proxy` 均值 **1.2627**、中位 **1.2288**、**53/60** 低估 / **6/60** 高估 / 1 相等（n=60；`ascii_only` n=47 均值 1.2594、`non_ascii_other` n=13 均值 1.2746），见 `audit-r12-scratch/repair-p2-5-2026-09-29/token_proxy_calibration.offline.json`。**该重放不是逐位确定的**（据 task-1 记录，第二次重跑给出 1.2623），所以**任何校准数字都必须带自己的 n**，不得当成可复算常数。**端点交叉核对那一节属于测试方下一次校准的范围**：本条不据修复前的产物下交叉核对结论。**下面的三条定性结论不因此改变**（代理既不是上界也不是下界、形状依赖、无单一修正系数、头条量级跨轮不可复现），**CJK 278 字符 / 284 real token 的反例照旧成立**。

由此三条结论必须一起写：

1. **`len//4` 既不是上界也不是下界**：它**形状依赖**（英文散文被高估、CJK/JSON/hex/base64 被低估），**不存在单一修正系数**，不得用「乘以某个系数」换算真实 token。
2. **头条量级不可跨轮复现**：本仓库旧版本此处写「代理低估约 33%（`real/proxy` 均值 1.5617，59/60 `real > proxy`）」——那是**更早一轮**的头条量级；C27 逐轮历史里同口径的上一轮重放是均值 1.5613 / 中位 1.4914 / 60-60，2026-09-26 那次是 1.2498 / 49-60（当时写作「约 16.5%」），本轮在**修复前产物**上是 1.2442 / 52-60（当时写作「约 16.9%」；修复后离线重算是 1.2627 / 53-60）。方向与形状依赖稳定，**具体百分比不稳定**：任何「代理低估约 N%」的表述必须带上**本轮自己的 n 与区间**，不得把「约 33%」或「约 16.9%」当成常数。
3. **硬要求（不变）**：token 类声明必须同时给出 `len//4` 口径与**真实 tokenizer 口径**（至少在一个可复算的子集上）。两者方向不一致时，以真实 tokenizer 为准并写明。

**三种 token 口径不得互换、不得平均**（逐字使用；口径总表见 `docs/claims-and-evidence.md` §1.5）：

| 口径 | 数的是什么 | 不是什么 |
|---|---|---|
| `observation_tokens`（代理） | `max(1, len(text)//4)`，对**交付的观察文本**计数 | **不是**端点输入 usage，**不是**花费 |
| 端点 `usage`（本轮 round-14 证据所用的「真实 tokenizer 口径」） | 端点自己报的 usage，**跨每一次请求累加**（system prompt + tool schema + **重发的历史** + reasoning） | **不是**某一次请求的 system prompt／schema 大小；也**不等于** `cl100k_base`；**不是**花费 |
| `cl100k_base` 重放（C27） | 对**同一份抽样观察文本**的独立 BPE 计数 | **不是**被测模型的 tokenizer，**不是**整轮 usage |

因此：①端点 `usage` 与 `cl100k_base` 重放**不得相加、相减、平均**，也不得用后者去修正前者；②「D 的 system prompt 比 A 大 N%」这类话**不能**从端点 `usage.prompt_tokens` 的均值推出——那是**累加输入**，不是单次提示词大小；③引用 round-14 的「真实 tokenizer 口径」时必须写明它是**端点 `usage`（累加输入/输出）**，与 C27 的 `cl100k_base` 是不同口径。

## 5. 反模式清单（会被判失格的写法）

| 反模式 | 为什么失格 | 正确写法 |
|---|---|---|
| 只报点估计 | 无法区分结果与噪声 | 报区间 + 检出限 |
| 用独立两样本检验处理配对数据 | 检验选错，功效被低估 | 用 McNemar / 配对 t |
| 样本不足就下结论 | 用噪声当结果 | 先跑 `acceptance_power.py`，报"未检出" |
| 点估计在门槛错误一侧就宣称"产品缺口" | 点估计会随样本移动；区间跨到可达成一侧时这是**无证据**，说成产品缺口会让人停止收集本该继续的数据 | 只有**整个 CI95** 在错误一侧才标 `impossible_by_sample_size` / `gap_type=product_gap` |
| 拿最快的操作当 headline | 挑选有利样本 | 取**最差**操作 |
| 只比每轮 token 不比 CPST | 奖励失败 | 主终点用 CPST + 成功率非劣 |
| A 侧给稻草人提示 | 把提示词工程算成接口收益 | 补 C1 等量提示对照 |
| 混用 mock 与 live 数字 | 口径污染 | mock 只作管线自检（C1/C2），live 单独登记（C13） |
| 跨任务集版本直接比成功率 | 谓词改过，分母不同 | 引用必带 `task_set_version` |
| 用 `len//4` 当"token"写结论 | 代理**既不是上界也不是下界**、形状依赖（**修复前产物**读数：均值 1.2442、52/60 低估、7/60 高估；修复后离线重算 1.2627、53/60 低估）且头条量级跨轮不可复现 | 标口径，并给真实 tokenizer 对照（C27）；「低估约 N%」必须带本轮 n 与区间 |
| **用"能通过"的 fixture 去测契约** | 检查看起来是绿的，缺陷却活着 | **fixture 必须踩到边界之外**：C26 用 3 行文件测 `file.view`，恰好落在 >10 行不输出的例外里，于是「客户端把内容吞掉」这个缺陷长期不可见（C30）。补 60 行 + 默认参数，并做**负对照**（套回旧规则必须判 FAIL） |
