## 1. 被测对象

**VerseShell**：Rust 写的 agent 工具接口（ACI），二进制 `ae`。把「读写文件、跑命令、检索仓库」做成
**结构化 typed op**（`file.view` / `file.read_many` / `file.replace_exact` / `exec.run` / `repo.search` …），
返回结构化观察信封，而不是让模型拼 shell 命令。

**核心待验主张**：用 ACI 比用裸 shell **更省 token、更少步骤、成功率更高**，且与 PowerShell/Git Bash 有量级差距。

**当前一句话结论**（细节与限定语见 §4）：
> 在第一个两个预算都不构成约束的样本上，观察 token 口径下 ACI **确实更省**（L1/L2/L3 全部达标），
> **但对提示词等量对照的优势余量只有 0.021**；**真实 tokenizer 口径下方向相反**（总 token 是裸 shell 的 1.08 倍、
> 等量提示对照的 1.27 倍）；成功率优势 **+0.04，低于当前样本的检出限 0.1121（未检出）**。

## 2. 实验方案（完整）

### 2.1 三臂设计

| 臂 | 条件名 | 工具集 | 系统提示 | 作用 |
|---|---|---|---|---|
| **A** | `raw_shell` | 只有 `run_command` + `task_complete` | `SHELL_SYSTEM_PROMPT`（中性 shell 提示） | 主对照：裸 shell |
| **A′** | `raw_shell_coached` | 同 A | `COACHED_SHELL_PROMPT`（**与 D 同等详细、同结构、同规则条数**，但用 shell 语言表述） | **提示词等量对照**：唯一能把「接口功劳」与「提示词功劳」分开的一支 |
| **D** | `verseshell_aci` | 全套 typed op | ACI 系统提示 | 被测对象 |

**只有 D vs A′ 能归因于接口本身。** D vs A 仍含「提示词写得好」的混杂。

### 2.2 任务集

- `task_set_version = 2.0.0`，**25 个任务 = 10 个手写 + 15 个 LLM 生成并通过机械准入**，已冻结
  （`eval/task_set_freeze.json`，含清单与内容指纹）
- 语言分布（`lang` 字段取值）：`python 13`、`rust 6`、`typescript 2`、`ts 2`、`windows 2`
  —— **`windows` 是任务类别不是语言，`ts`/`typescript` 是同一门语言的两种写法**（已知数据质量问题，见 §3 的 E14）
- **与预注册的偏差**：预注册要求 **30 个生成任务**，实际只准入 **15 个**（原因：端点不可靠）；
  **组合规则一条没放松**（≥3 语言、每任务 ≥2 个独立正确解、观察量分层、规模上限），**只有数量未达标**
- **构造效度问题**：准入的 15 个里只有 **4 个** pristine 观察 ≥1000 token，占整个任务集的 **16%**
  （预注册要求 1/3）——token 类结论仍主要建立在**小观察**上

### 2.3 模型与端点

- 模型：**`sn-glm-5-3-flash`**（单模型；本地 OpenAI 兼容端点 `http://127.0.0.1:3065/v1`，
  由 `workbuddy-proxy-desktop.exe` 提供）
- 这是**推理模型**：它会把 completion 预算烧在 `reasoning_content` 上
- `temperature = 0`，`max_tokens = 16384`（单轮 completion），`max_turns = 20`（整轮步数）
- 端点**接受 `seed` 但不严格复现**

### 2.4 预算纪律（§3.3 / 验收标准 §0.5）

> 任何「每次运行的预算上限」（`max_turns` / `max_tokens`）都必须先证明**没有在不对称地截断某一个臂**。
> **任一侧撞上限 >10% 即视为上限构成约束，必须提高上限重跑**，且报告时必须同时给出三臂截断率。

**第 13 轮实测满足**：步数上限 0%/0%/0%、completion 上限 **3%/7%/4%**、`harness_crash` 全 0
（`eval/three_arm_report.json` 的 `at_cap_rate` / `at_token_cap_rate`）。

### 2.5 预注册与门禁

- 门槛参数在 `tools/acceptance_power.py::PREREG` 与 `docs/acceptance-criteria.md` 中必须逐字一致
- 三条通用纪律：**预注册**（MDE／口径／最小样本量在看数据前写死）、**区间优先**（区间必须越过门槛那一侧）、
  **区分数据缺口与产品缺口**（只有**整个 CI95 落在门槛错误一侧**才算产品缺口，否则记「无证据」）
- 门禁 25 项：`python tools/claim_gate.py` → **23/25**

## 5. 消融实验（`read_files` 隐藏）与它的一次失败

### 5.1 第 12 轮那次消融的结论已被推翻

- 第 12 轮记录：隐藏 `read_files` 后 **D 成功率 0.32**，据此得出「D 高度依赖读工具」
- 复核发现三件事：①`read_files` 是 AE 的 **`file.read_many`（批量读）**，单文件读 `read_file`=`file.view`
  **仍然可用且被用了 24 次**，所以这不是「拿掉读工具」；②消融 D 臂 **13/25 行**是
  `completion_truncated_turns=1` + **0 次工具调用**，剔除后 D = **0.667** 而非 0.32；
  ③同轮 A/A′ 配置未变但数字也动了（运行间漂移）
- **处置**：用不构成约束的预算重跑 without 臂

### 5.2 重跑失败（E15/E16 的现场证据）

- 命令：`python tools/live_round.py --tag tf0100 --arms without --seeds 42,43,44 --max-turns 20`
- **seed 42（23:23）与 seed 43（00:35）成功**；**seed 44 在 01:25 挂死在任务
  `rust_borrow_fix_longest_word_a4c895ec` 的 D 臂**，挂到 12:52 才发现——**整整 11.5 小时**
- 挂死命令：`python -c "open('src/lib.rs','w').write(open('CON','r').read())"`（PID 31616）
- 因为 E16（整轮结束才落盘），**seed 44 已完成的 61 行全部丢失**，文件从未写出
- 处置：杀掉挂死进程与 runner，**没有**把 2 个 seed 当 3 个用，**没有**用未完成数据凑数
- 本轮消融因此只有 **2 个 seed / 50 个配对格**

| 观察 token/轮 | 558.1 | 543.4 | ×0.9736 |

**逐 seed 方向相反**：seed 42 为 0.80→0.88（+0.08），seed 43 为 0.92→0.84（−0.08）。

**结论**：**P7 撤回。**去掉批量读的**唯一稳定代价是多约 21% 的工具调用**；成功率无可检出的下降；
观察 token 基本不变。第 12 轮的 0.32 是 completion 截断造成的假象。

### 5.4 顺带测到的运行间漂移（A/A′ 配置完全相同）

| 臂 | with 臂（2 seed 聚合） | without 臂（同配置） | 差 |
|---|---|---|---|
| A 成功率 | 0.8800 | 0.8400 | **−0.04** |
| A′ 成功率 | 0.8400 | 0.8000 | **−0.04** |
| A 观察 token | 1121.6 | 1152.4 | +2.7% |
| A′ 观察 token | 759.9 | 801.0 | +5.4% |

这是在**预算不构成约束**的干净条件下测到的**同配置重跑**差异——直接量化了端点非确定性。

## 6. 已知短板（**请优先攻击这里**）

1. **没有留出集（最大的方法论缺口）**。全部结论来自同一批 25 个任务，而 E1–E13 里的多数缺陷
   **正是在这批任务上发现并修掉的**——相当于在测试集上调过参。§2.2 的扩充计划（30 个候选）
   与留出集设计**尚未执行**。
2. **单模型、单端点、单机**。全部 live 结论来自 `sn-glm-5-3-flash` 一台机器，不可外推。
   端点**时变**已被三次测量证实：completion 截断率 0%→12%；同配置重跑 A′ 成功率 −0.04、
   观察 token +5.4%；tokenizer 校准的头条量级三轮三个值（`real/proxy` 均值 **1.5613 → 1.2498 → 1.2885**）。
3. **「省 token」这句话依赖口径选择**。代理口径（`len(text)//4`）与真实 tokenizer 口径
   **方向相反**：观察 token 0.56–0.80（更省），真实总 token 1.076–1.265（更贵）。
   而 `len//4` 代理已被校准证明**不是上界**（52/60 样本 `real > proxy`，形状依赖、无单一修正系数）。
4. **输出/输入的权衡没有被对外说明清楚**。D 把输出 token 砍到约一半（0.507），
   却把输入抬高 22%–49%（prompt D/A 1.2211 / D/A′ 1.4865），总账 1.076（A）/ 1.265（A′）。
   「省 token」若只报观察 token，是**只报有利的一半**。
5. **C14/C16 是唯一未修的门禁红**：两条声明要求「占读桶总量的百分比」，而这个量随读法混合漂移。
   需要产品决策：修产品使投影在内容主导读法上也省 ≥10%，或**显式**把声明改成「信封开销削减 ≥40%」
   并在新数据上验证。**当前门禁红得有道理。**
6. **任务集独立性无法事后验证**：15/25 是 LLM 生成的，生成器与变体模型来自同一端点家族；
   `provenance.independent_of` 依赖生成时的提示隔离。
7. **大观察任务只占 16%**（预注册要求 1/3），token 类结论的构造效度偏弱。
8. **推理模型的 reasoning token 不进观察 token 口径**，却进真实 token 口径（这是 3 与 4 的根因之一）。
   completion 预算仍偶发被 reasoning 烧穿（3%–7%），且**会随时间漂移**。
9. **本自述不是独立复核**：撰写者就是执行者。第 12 轮曾有一份真正的第三方审计，
   它找出的问题（区间口径、CPST 漏报 A′、命名错误）我们**已逐条落地**，
   但它**拿不到仓库**，只能做内部一致性复算。
10. **消融只有 2 个 seed，且逐 seed 方向相反**（§5.3）——「批量读无成功率效应」这个结论的
    区间很宽，不能当强结论。
11. **E15 意味着历史数据可能在未知处被污染**：只要模型曾经发出过阻塞设备命令，
    那一轮就会被挂死或静默变慢，而**产物里看不出来**（它只记 `completion_truncated_turns`）。
    第 12 轮那 13 行截断里有没有这种行，**无法事后判断**。
12. **成功率的「未检出」不等于「无差异」**：Δ=+0.04，配对区间 **[−0.038, 0.118]**，
    检出限 0.1121。样本能排除的是「≥0.1121 的优势」，不能排除「+0.05 的小优势」。
13. **跨 shell 的「快 2 倍」有误导风险**：它只对 **PowerShell** 成立；而基线臂实际跑的是 **cmd.exe**，
    对 cmd.exe **没有优势**（CPU info 慢 3.0 倍）。且工具时间只占一轮墙钟的 2.3%–6.9%。
14. **`check_gate` 的 24→25 项里，真正测「产品能力」的只有少数几类**：多数是 mock / cargo_test /
    content_fingerprint 等**自检**，测的是管线与契约，**不测模型能力**。「门禁绿」≠「产品结论成立」。

## 8. 一句话总结（请核对是否与 §4 一致）

> 第 13 轮是**第一个两个预算都不构成约束、且证据全部新鲜**的样本（completion 截断 3%/7%/4%、
> harness 崩溃 0/0/0）。在这一轮：观察 token 口径下 ACI **确实更省**（L1/L2/L3 全部达标，
> 对照提示词等量臂 **0.7990，上界 0.9788，余量仅 0.021**）；工具调用数仍无证据（0.8957，区间跨 1.0）；
> 成功率 **+0.04，低于检出限 0.1121（未检出）**；而**真实 tokenizer 口径方向相反**
> （总 token 是裸 shell 的 1.076 倍、是提示词等量对照的 **1.265 倍，整段区间在 1.0 之上**）。
> 与第 12 轮「定版」同条件重跑，头条成功率差从 **+0.12/+0.16 掉到 +0.04/+0.04**——
> 因为第 12 轮的 A/A′ 各有 11%/15% 的轮次被 completion 上限截断，而**被截断的轮次不发工具调用、
> 直接记失败**，系统性压低了基线。跨 shell 的「快 ≥2 倍」只对 PowerShell 成立，对基线臂实际使用的
> cmd.exe 没有优势。消融的「D 高度依赖读工具」**已被推翻**（去掉批量读的唯一稳定代价是多 21% 工具调用，
> 成功率净效应为 0）。**而最该被审计的是：这套东西的头条数字被 16 条测量缺陷轮流改写过了，
> 没有留出集，而且刚刚有一次整轮实验被一个 `open('CON','r')` 的命令静默挂死了 11.5 小时。**
