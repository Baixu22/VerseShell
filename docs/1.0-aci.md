# VerseShell 1.0 ACI Surface

Agent integrations should call **typed operations** over JSON-RPC (`op`) or MCP
(auto-generated tool names with `.` → `_`).

## Core

| Op | MCP | Purpose |
|----|-----|---------|

| `result.query` | `result_query` | Artifact head/tail/grep/raw |

## File

| Op | Notes |
|----|-------|
| `file.view` | cursor + window; returns `content_hash` (full) and `hash` (compact) |
| `file.read_many` | up to 8 files in one call; per-file `content_hash` / `hash` / `total_lines` / window; `windows[]` per-file overrides and a `max_total_lines` batch budget, with `truncated` / `next_start_line` pagination; a missing entry is reported per file |
| `file.read_range` | start/end lines, max 500 default; returns `content_hash` + `hash` |
| `file.hash` | `sha256:…` for expected_hash |
| `file.replace_exact` | unique match; `E_AMBIGUOUS` / `E_STALE_HASH` |
| `file.apply_patch` | ordered patches; fails closed if any miss |
| `file.edit_range` | line range replace; optional `check` |
| `file.diff` | simple line diff vs `new_text` |
| `file.remove` | agent mode → trash + `restore_token` |

### Read envelope: compact digest and batch budget

A read op returns the digest twice:

- `content_hash` — the full `sha256:<64 hex>` string (unchanged contract).
- `hash` — the first 16 hex characters of the same digest.

`expected_hash` on the write ops accepts either form, plus any unambiguous hex
prefix of at least 8 characters, so an agent can hand back the short `hash`
unchanged. A full digest still compares exactly; a wrong prefix still fails with
`E_STALE_HASH` and `data.actual_hash` for a one-step retry. A 16-hex prefix is
64 bits, so a stale read is accepted only on a 2^-64 collision against the
current content.

`file.read_many` additionally takes:

| Arg | Default | Meaning |
|-----|---------|---------|
| `windows[]` | — | Per-file `{start_line, window}`, aligned by index with `paths`; a shorter array leaves the rest on the defaults |
| `window` | 80 | Default per-file line window |
| `max_total_lines` | 240 | Budget for the whole batch, in returned lines |

Each entry reports `start_line` / `end_line` / `truncated` / `deferred` /
`next_start_line`. An entry cut by its own window is `truncated`; an entry that
no longer fits the batch budget comes back empty and `deferred`. Both carry
`next_start_line`, so a bounded batch stays paginable instead of silently
dropping files. `data` carries `lines_returned`, `max_total_lines` and
`deferred` so a client can see the budget was hit.

The `lines` shape stays `[{line, text}, …]`. Measured on the frozen live
trajectory (claim C14), the per-line wrapper is not what costs tokens — the
dominant overheads are the 71-character full digest per file and the per-entry
key names. Keeping `lines` therefore avoids breaking consumers, and the compact
`hash` is additive: a consumer that reads `content_hash` keeps working.

## Process lifecycle

`exec.run` stays one-shot. Long-lived, runtime-owned processes use the five
`process.*` ops below. They are available over JSON-RPC `op` and are
intentionally **not** registered as MCP tools: stateful lifecycle stays on the
host-owned JSONL transport (`src/mcp/tools.rs` skips `process.*`). Their
`mcp_name` appears only in `ops.list` / the operation catalog.

| Op | MCP | Purpose |
|----|-----|---------|
| `process.start` | `process_start` | Start an argv process owned by this runtime; returns identity + first snapshot |
| `process.poll` | `process_poll` | Read bounded output from a monotonic byte cursor and observe state |
| `process.write` | `process_write` | Write bounded input (or EOF) to an owned pipe / PTY process |
| `process.kill` | `process_kill` | Idempotently terminate the owned process tree and observe converged state |
| `process.list` | `process_list` | List lifecycle records scoped to one runtime / agent / session |

`process.start` inputs: `argv` (required), `agent_id` + `session_id` (required),
`cwd` (default `.`), `env`, `stdin_mode` (`null` \| `pipe`, default `null`),
`stdin` / `stdin_encoding` / `stdin_eof`, `pty` (default `false`), `cols` / `rows`
(default 120 x 30), `timeout_ms`, `max_output_bytes` (default 64 MiB),
`max_memory_mb`, `max_processes`, `wait_ms` (default `0`).
`poll` takes `process_id` + `runtime_id` + `agent_id` + `session_id` (all
required), plus `cursor`, `max_bytes`, `wait_ms`. `write` takes the same owner
quadruple plus `data`, `encoding`, `submit`, `eof`. `kill` adds `reason`
(default `manual_cancel`) and `wait_ms` (default 2000). `list` takes
`runtime_id` + `agent_id` + `session_id` and optional `include_terminal`.

### Ownership

`process_id` is `proc_<uuid>` and `runtime_id` is `rt_<uuid>` (one per server
process). Clients must **echo** `runtime_id`, `agent_id` and `session_id` back
on `poll` / `write` / `kill` / `list`; `agent_id` must also equal the request
envelope's `agent`. A mismatch returns `E_PROCESS_OWNER`.

- Matching is against the record's stored owner, not against the currently
  running manager, so after a restart the **old** `runtime_id` still addresses
  the record.
- `session_id` is a plain string match. It is not a session lease and must not
  be treated as a security boundary.
- `list` filters by runtime / agent / session only; there is no workspace
  argument. A manager is bound to one workspace for its lifetime; binding it to
  another returns `E_PROCESS_WORKSPACE`.

### Snapshot fields

`start`, `poll` and `kill` return a `snapshot`:

- state: `starting` \| `running` \| `exited` \| `killed` \| `lost` (the start
  path produces `running`; `starting` is only matched during restart
  reconciliation), plus `pid`, `argv`, `cwd`, `executable`, `interpreter`,
  `mode` (`pipe` \| `pty`), `stdin_mode`, `started_at_ms`, `updated_at_ms`,
  `exited_at_ms`, `exit_code` (`-1` when unavailable), `termination_reason`,
  `timed_out`, `retention_expires_at_ms`.
- output: `chunks[{stream,start_cursor,end_cursor,encoding,text}]`,
  `requested_cursor`, `cursor`, `next_cursor`, `retained_start_cursor`,
  `lost_bytes`, `truncated`, `returned_bytes`.
- artifacts: emitted once at terminal state (`kind: process.lifecycle`).

`process.write` returns `{process_id, written_bytes, eof}`; `process.list`
returns `{runtime_id, workspace_id, processes[], count}`.

### Cursor, output window and waiting

- `next_cursor` is monotonic (never decreases). Asking for a `cursor` beyond it
  returns `E_PROCESS_CURSOR`; a cursor that has aged out is clamped to
  `retained_start_cursor` and reported through `lost_bytes` / `truncated`.
- `max_bytes` defaults to 65536 and is clamped to 262144 per call.
- `max_output_bytes` at start is a **rolling retained window**, not a hard cap
  on total output. Evicted bytes are counted in `lost_bytes`; full raw bytes are
  only recoverable through the terminal-state artifacts.
- `wait_ms` blocks until new output, terminal state or expiry, and is clamped to
  30000 on every path.
- `timeout_ms` (start) `0` means no limit; on expiry the tree is terminated and
  the record ends `killed` with `timed_out: true`,
  `termination_reason: "timeout"`.

### Termination, retention and restart

- Tree termination: Windows Job Objects (`KILL_ON_JOB_CLOSE` +
  `TerminateJobObject`) for both the pipe and ConPTY paths; Unix process groups
  with `SIGKILL`.
- `kill` is idempotent: an already-terminal record is not re-terminated and an
  existing `termination_reason` is not overwritten. It returns once the wait
  budget expires, so a returned snapshot does not by itself prove the tree is
  gone.
- Records are retained 24 h and pruned during the next start-up reconciliation;
  there is no background sweeper while the server runs.
- Server shutdown marks live records `runtime_shutdown`; on restart,
  `starting` / `running` records become `lost` with
  `termination_reason: "runtime_restart_unrecoverable"` and their stdin becomes
  a no-op. `poll` / `kill` on a `lost` record still answer, but no longer act.

### PTY (Windows ConPTY)

- `pty: true` is Windows-only; other builds return
  `E_PROCESS_PTY_UNSUPPORTED`.
- `cols` / `rows` map to the pseudo-console size and must be positive.
- A PTY process exposes a single `pty` stream (no separate `stderr`), and its
  stdin writer always exists regardless of `stdin_mode`.
- The pipe path keeps `stdout` / `stderr` separate and adds
  `CREATE_NO_WINDOW` on Windows.

### Approval and capability

- All five ops require capability `shell.exec`; denial returns
  `E_CAPABILITY_DENY`.
- Only `process.start` passes through `safety::guard` (effect `exec`, not
  reversible). In agent mode it returns `E_NEEDS_APPROVAL` with
  `error.hint` + `data.approval_token` unless `AETHER_APPROVE_ALL` /
  `AETHER_APPROVE=<token>` applies. `poll` / `write` / `kill` / `list` do not
  re-prompt.

### Error codes

| Code | Trigger |
|------|---------|
| `E_PROCESS_BAD_ARG` | malformed args: empty argv, blank owner ids, bad `stdin_mode`, stdin without `stdin_mode=pipe`, out-of-range `max_output_bytes`, zero PTY size |
| `E_PROCESS_OWNER` | `agent_id` mismatch, or the echoed owner does not match the record |
| `E_PROCESS_WORKSPACE` | lifecycle manager already bound to another workspace |
| `E_PROCESS_NOT_FOUND` | unknown `process_id` |
| `E_PROCESS_CURSOR` | requested cursor beyond `next_cursor` |
| `E_PROCESS_CWD` | `cwd` unresolvable, outside the workspace, or not a directory |
| `E_PROCESS_ENV` | too many env entries, invalid key/value, or over the byte budget |
| `E_PROCESS_INPUT` | invalid base64, bad encoding, or input over the size limit |
| `E_PROCESS_SPAWN` | spawn failed or a stdio pipe was unavailable |
| `E_PROCESS_PERSIST` | could not persist the starting record |
| `E_PROCESS_EXITED` | write to an already-terminal process |
| `E_PROCESS_STDIN_CLOSED` | no stdin writer (e.g. `stdin_mode=null`) |
| `E_PROCESS_WRITE` | stdin write/flush failed |
| `E_PROCESS_KILL` | terminating the tree failed |
| `E_PROCESS_PTY` / `E_PROCESS_JOB` / `E_PROCESS_WIN32` | ConPTY creation, job attach, or other Win32 call failed |
| `E_PROCESS_PTY_UNSUPPORTED` | `pty: true` on a build without a PTY backend |
| `E_PROCESS_INTERNAL` | failure without a recognised `E_` code |

`runtime.handshake` advertises the feature flags `process_lifecycle`,
`monotonic_process_cursor` and `windows_conpty`.

### Notes and boundaries

- `env` **replaces** the inherited environment (`env_clear` + the given entries);
  omit `env` to inherit. It is not merged.
- `process.write` with `submit: true` appends a carriage return. The pipe and PTY
  paths treat it the same way today.
- All `process.*` failures are reported as `recoverable: true`, including
  argument and ownership errors.
- `spec.effect` (`process.spawn` / `process.read` / `process.write` /
  `process.kill`) is catalog metadata; successful observations carry
  `meta.effects: ["process"]`.
- `max_memory_mb` / `max_processes` are applied through the Windows Job Object on
  the lifecycle path as well. The Unix lifecycle path has no equivalent
  enforcement and does not error; the one-shot runner instead rejects those
  limits on non-Windows with `E_LIMIT_UNSUPPORTED`.
- Evidence boundary: the lifecycle acceptance tests are Windows-only
  (`tests/process_lifecycle_tests.rs` is `#![cfg(windows)]`), so the pipe, PTY
  and restart-reconciliation claims are proven on Windows only; the Unix process
  group path is not covered by those tests.

## Observation contract

All ops return `verseshell.observation/v1` with `ok`, `data`/`error`,
`diagnostics`, `meta`, `suggested_next`.

On `E_NEEDS_APPROVAL`, `error.hint` carries the retry path (`AETHER_APPROVE=<token>`
or `approve("…")`), and `data.approval_token` may be present.

Legacy `cmd` / MCP `exec` / `eval` remain for the 1.x series as secondary APIs.

## Acceptance closed loop

The Coder Agent happy path is covered by
`tests/aci_1_0_closed_loop_acceptance.rs`:

1. `ops.list` → file view/read/hash → repo search/summary
2. `tx.begin` → edit → `tx.commit` / `tx.rollback`
3. lint / stale-hash / ambiguous failure codes
4. `exec.run` success silence + failure artifact → `result.query` raw recovery
5. `test.run_target` + `test.summarize_last`
6. `file.remove` (trash) → `tx.restore` (including across server restarts)

### Agent env for exec / tests

| Env | Purpose |
|-----|---------|
| `AETHER_MODE=agent` | Agent policy (sandbox + approval for exec) |
| `AETHER_WORKSPACE` | Workspace jail root |
| `AETHER_APPROVE_ALL=1` | CI / local auto-approve for `exec.run` / hard deletes |
| `AETHER_APPROVE=<token>` | Approve one action token from `error.hint` |

Production agents should use per-action tokens, not `AETHER_APPROVE_ALL`.

### Client notes

- Send **UTF-8 without BOM**, line-delimited JSON on stdin.
- PowerShell `Get-Content | ae --serve` may inject a BOM on the first line and
  yield `E_PARSE`; prefer raw byte writes or `cmd /c type file.jsonl | ae --serve`.
