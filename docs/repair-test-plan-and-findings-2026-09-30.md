## 第三部分 · C14 / C16 为什么 FAIL，错在哪一层

### 3.0 先分清两件事

- **C14/C16 的 FAIL 不是"代码出错"**。门禁的作用就是把"现在不能主张的事"如实标红；它们红了，说明这两条**声明**没达到自己预注册的门槛。**这是正确行为**，不是 bug。
- 真正算"错误/弊病"的是 §2.1 的那 8 项（计量 bug、混轮、指纹缺口、非确定性……），它们**都已修**。

### 3.1 两条声明各测什么

| | C14 | C16 |
|---|---|---|
| 门槛 | 节省 **≥ 0.15** | 节省 **≥ 0.10** |
| 量什么 | 冻结 read 调用集上，**批量读信封**（compact digest + 有界批预算）相对 legacy 的代理 token 节省 | 参考客户端**紧凑读投影**在冻结轨迹上的节省 |
| 工具 | `tools/tf45_envelope_replay.py` | `tools/read_path_breakdown.py` |
| r15 实测 | 144 条冻结调用、141 条可精确复现、3 条排除；**74280 → 70940 token = 0.045** | 141 条可复现；**77017 → 70940 token = 0.0789**（字符 308325 → 283972） |
| 与模型的关系 | **无关**：客户端渲染的离线重放，不是模型行为测量 | **无关**：同上 |

### 3.2 为什么 C16 过不了（算术）

r15 的字符占比（改动前）：

| 分量 | 占比 |
|---|---:|
| **content（文件正文）** | **77.5%** |
| line_wrapper（行包装） | 10.8% |
| residual | 4.6% |
| counts | 2.8% |
| digest | 2.8% |
| path | 1.5% |

紧凑投影**只动 line_wrapper + counts（合计 13.6%）**，并且拿掉了其中 57.4%（这就是 C34 = 0.5736 的含义）。
于是总桶上的效果上限天然就是 `13.6% × 57.4% ≈ 7.8%`——实测 **7.9%**，与算术吻合。

**在"键值 JSON + 16-hex digest + 保留全部值"的现有 schema 下，天花板是 9.68%**（即使把每个 key 压到 1 字符、
再砍掉剩余 counts），仍然差 0.32 个百分点。能过线的路子都要**改变模型看到的信息**：

| 方案 | C16 | 信息 | 代价 |
|---|---:|---|---|
| 位置化数组 schema | **10.94%** | 无损 | 换 schema ⇒ 现有行为类数字全部失效，**须重跑 live** |
| 文本框架（不再是 JSON） | **15.00%** | 无损 | 观测面改动更大 |
| 砍/缩 digest | 10.35–10.75% | **有损**（削掉 stale-write 令牌） | 而且会把 **C14 打到 0** |
| 内容去重（重复读未变文件只回引用） | 6.73% | 有损于"逐字可读" | 投递 token −35.2%，但**让 C16 变差**（两条腿同时缩小） |
| 缩小窗口 | ≤9.97% | 有损 | 需要 k ≥ 0.02 才有意义 |

### 3.3 为什么 C14 过不了（算术）

C14 的**分子结构上只有 digest**：legacy 腿 = 同一信封把 `hash` 去掉后回填 71 字符全长 content_hash，
共 **224 处 × 55 字符 = 12320 字符 = 3074 token**。
即使把信封 hash 压到 **1 个字符**，上限也只有 **3916 token = 6.63%**。
要够到 0.15，必须把今天渲染的行只留 **k ≤ 0.156**，也就是**只给模型看今天内容的 16–24%**——
那不是"省 token"，那是让冻结轨迹失效（模型会去分页/重读）。把 `hash` 清空或只在 compact 分支改 digest 格式，都得到 **0**。

### 3.4 "错在哪一层"的一览

| 层次 | 状况 | 性质 |
|---|---|---|
| 产品能力 | 投影只压缩"命名信封"这一小块（13.6%） | **设计缺口**：内容是 77.5%，不动内容就动不了总量 |
| 声明规格 | C14 分子结构上只有 digest；C16 门槛 10% 高于现有 schema 天花板 9.68% | **声明与产品不匹配**：门槛是预注册的，不许事后下调（TF-0116） |
| 度量实现 | 两者都是冻结调用集上的离线重放，口径正确、可复算 | **无缺陷** |
| 门禁判定 | FAIL 正确 | **不是 bug**；C34 = 0.5736 是这两条的**可主张替代** |
| 处置 | 用户 2026-09-29 决定 **no-go**：保留 FAIL、不动阈值 | 见 `DECISION-c14-c16.md` |

|---|---|---|---|
| `A-S` | A 填充到 L | — | 共同短目标 |
| `A-L` | A-S 追加 delta | A-S | A 内的填充效应 |
| `D-S` | D 填充到 L | — | 共同短目标 |
| `D-L` | D-S 追加同一 delta | D-S / A-L | D 内填充效应 / 共同长目标下框架差异 |

长度用 Unicode 码点数匹配，另记录 UTF-8 字节数；usage 的 15% 等长检查只用于共同目标，不能用于故意拉开的长短对。
不按事后结局/usage 剔除重复或格；不显著只表示证据不足，不是排除原因。填充可能有语义影响，必须披露。
L、delta、逐字提示、功效论证、四臂运行/分析程序及 manifest 尚需完成并冻结。
**L1 的格永不进入正式验收数据**（独立目录/manifest/checkpoint）。

### 5.3 端点容量、重试与中断规则（本轮血的教训）

- **300 秒非流式上限是历史已记录约束**（P0-3 未解决），改变端点配置后须重测。
  r15 在 `max_tokens=16384` 下仍发生过 29 格 502（tls handshake eof），不能写成“未见 502”；
  它们不证明与 300s 超时是同一原因。
- **端点曾整段不可用**：本轮中断影响 **29/315 = 9.2%** 的 with 臂；一次事件不能估计未来必然发生的概率，因此：
  - 逐格 checkpoint（已具备）+ 逐 seed 分片（已具备）；
  - **只补跑 `endpoint_failure` 行**，从 sidecar 摘掉这些行后重跑该分片，被替换行存档；
  - **不重试模型解题失败**；
  - 每次补跑都记录时间块，并在引用该批对比时同时引用"条件与端点时变的平衡在补跑格上不成立"。
- **并发**：不要与其他重 CPU 任务（如 `task_admissibility` 全池 ~12 分钟）同时跑 live，避免工具超时污染格子。
- **单臂 vs 双臂**：只跑 with 臂会让 C35（配对对照臂组成一致）变红——**不要单臂采**。
- **中途改配置**：若必须改模型可见面，另起研究版本、保留旧批次，**不得只补 D 的不利格后与旧 A 比**。
