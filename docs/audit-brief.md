## 1. 被测对象

**VerseShell**：一个 Rust 写的 agent 工具接口（ACI），二进制 `ae`。它把「读写文件、跑命令、
检索仓库」这些动作做成**结构化 typed op**（`file.view` / `file.read_many` / `file.replace_exact` /
`exec.run` / `repo.search` …），返回**结构化观察信封**，而不是让模型去拼 shell 命令。

**对照组**：同一台机器上的裸 shell（`cmd.exe` / PowerShell 路径），即让模型直接发命令字符串。

**核心待验主张（仓库自己的）**：用 ACI 比用裸 shell **更省 token、更少步骤、成功率更高**，
并且**与 PowerShell/Git Bash 的启动性能有量级差距**。

## 2. 实验设计

### 2.1 三臂（这是本设计的关键）

| 臂 | 条件名 | 工具集 | 系统提示 | 作用 |
|---|---|---|---|---|
| **A** | `raw_shell` | 只有 `run_command` + `task_complete` | `SHELL_SYSTEM_PROMPT`（中性 shell 提示） | 主对照：裸 shell |
| **A′** | `raw_shell_coached` | 同 A | `COACHED_SHELL_PROMPT`（**与 D 同等详细**、同结构、同规则条数，但用 shell 语言表述） | **提示词等量对照**：唯一能把「接口功劳」与「提示词功劳」分开的一支 |
| **D** | `verseshell_aci` | 全套 typed op | ACI 系统提示 | 被测对象 |

**为什么必须有 A′**：D 侧系统提示里含 ACI 专属规则（「信任工具输出」「`exec.run` 只用于构建/测试/安装」等）。
若 A 只拿裸工具，比出来的可能是**提示词工程**而不是接口。**只有 `D vs A′` 能归因于接口本身。**

每行记录 `prompt_profile`，可追溯到是哪份简报产生的。

### 2.2 任务集（`task_set_version = 2.0.0`，**已冻结**）

- **25 个任务** = 10 个手写 + **15 个 LLM 生成并通过机械准入**
- 冻结记录：`eval/task_set_freeze.json`（含任务清单 + 内容指纹 `06c7866ee289a9ac`）
- **`lang` 字段取值分布**（**注意：这不是语言分布**——`windows` 是任务类别而非语言，`ts` 与 `typescript` 是同一门语言的两种写法；见 §6 问题 P6）：
  `python 13`、`rust 6`、`typescript 2`、`ts 2`、`windows 2`
- 分层：`existing 20`、`medium 3`、`large 1`、`small 1`
  （**`existing` 是 tier 桶的默认值，不是「手写」**：20 = 10 个手写 + 10 个没带 `tier` 字段的生成任务，
  出处 `tools/freeze_task_set.py` 的 `tier = prov.get("tier") or "existing"`；所以它和上面的「10 手写 + 15 生成」是两个不同的轴，不矛盾）
- 生成候选准入情况（`eval/task_admissibility.json`）：
  **35 个候选 → 准入 15、拒绝 20**

**与预注册的偏差（必须让审计者知道）**：预注册要求 **30 个生成任务**，实际只准入 **15 个**。
原因是端点不可靠（见 §5 缺陷 D6）。**组合规则未放松**（≥3 语言、每个任务 ≥2 个独立正确解、
观察量分层、规模上限），**只有数量未达标**。这条修订发生在**任何 live 测量之前**。

### 2.3 模型与端点

- 模型：**`sn-glm-5-3-flash`**（单模型，本地 OpenAI 兼容端点 `http://127.0.0.1:3065/v1`）
- 这是一个**推理模型**：它会把自己的 completion 预算烧在 `reasoning_content` 上（实测一次
  180 行请求：completion 16384、reasoning 16209、**content 输出 0 字符**）
- `temperature = 0`，`max_tokens = 16384`（单轮 completion），`max_turns = 20`（整轮步数）

### 2.4 定版 live 规模

**25 任务 × 3 条件 × 3 seeds（42/43/44）= 225 行真实调用**，`api_error` 行 = **0**。

**与预注册的偏差**：预注册是 30 任务 × 3 条件 × **5 seeds** ≈ 450 行。实际 3 seeds。
原因：端点吞吐（每 seed 约 60–90 分钟）。**后果**：成功率 MDE 0.15 需要 105 对，只有 75 对。

## 3. 验收标准（预注册）

门槛参数在 `tools/acceptance_power.py::PREREG` 与 `docs/acceptance-criteria.md` 中**必须逐字一致**。

### 3.1 三条通用纪律

| # | 纪律 | 挡住的失格写法 |
|---|---|---|
| 1 | **预注册**：MDE／口径／最小样本量必须在看数据之前写死 | 「门槛从 0.7 调到 0.8 之后就通过了」 |
| 2 | **区间优先**：任何「更省/更快」必须给区间，并让区间越过门槛那一侧 | 「D/A = 0.78，所以省了 22%」 |
| 3 | **区分数据缺口与产品缺口**：点估计已在门槛错误一侧时，加样本永远救不回来 | 「再跑几轮就能证明 ≤0.6」 |

### 3.2 四个验收区

**A 区：真实解决问题（成功率）**
- 配对单位 `(task_id, seed, run_index)`，用 **McNemar**（不用独立两样本 z）
- 预注册 **MDE = 0.15 绝对差**，α=0.05 双侧，power=0.80
- 判定：`n_pairs ≥ n_required` **且** `p < 0.05` **且** 配对差 CI95 不跨 0 **且** 观测效应 ≥ MDE

**B 区：与 PowerShell / Git Bash 的差距**
- 必须先证明命令**输出等价**（归一化比对，不只看退出码），再比时间
- 交错执行、预热丢弃 ≥3 次、配对到迭代、报**中位数**、**headline 取最差操作**
- 每操作每 shell ≥20 次迭代 + bootstrap CI95

**C 区：性能表现**
- 必须报 `p50/p90/p99`、冷启动 vs 预热、峰值 RSS、机器事实

**D 区：token 节省（最重要）**
- 三条硬要求：**配对对照**、**真实 tokenizer 口径**、**以成功为前提**
- 主终点是 **CPST = 观察 token 总量 / 成功数**（只比每轮 token 等于奖励失败）
- 观察 token 是 `max(1, len(text)//4)` 代理；**C27 实测该代理低估约 33%**（`real/proxy` 均值
  1.5617，59/60 样本 `real > proxy`），且**误差形状依赖**（CJK 低估约 4 倍、hex 摘要低估 1.8 倍），
  **不存在单一修正系数**

### 3.3 预算上限纪律（对应 `docs/acceptance-criteria.md` 的 §0.5，本轮新增）

任何「每次运行的预算上限」（`max_turns` / `max_tokens`）都必须先证明**没有在不对称地截断某一个臂**。
**任一侧撞上限 >10% 即视为上限构成约束，必须提高上限重跑**，且报告时必须同时给出三臂截断率。

### 4.4 结论（可写 / 不可写）

**可以写成肯定句的**
1. ✅ **跨 shell 性能**：5/5 操作严格更快、全部 ≥2 倍，最差一条约 4 倍
2. ✅ **D 比未加提示的裸 shell 省 31.5% 观察 token**（区间整体低于 1.0）
3. ✅ **省 ≥15%**、**每成功一次更便宜（CPST）**

**不能写的**
1. ❌ **「接口本身省 token」**——提示词拉平后 1.0567，与 1.0 不可区分
2. ❌ **「工具调用更少」**——1.0074
3. ❌ **「成功率更高」**——方向有利（+0.12）但**样本不足**，只能写「未检出」
4. ❌ **「达到冻结目标 0.60」**——产品缺口

| 门禁项 | 门槛 | 实测 | 产物 |
|---|---|---|---|
| **C14** 批量读取信封（紧凑摘要 + 预算） | ≥0.15 | **0.0514** | `eval/tf45_envelope_replay.json` |

## 5. 缺陷史（审计重点：每一个都曾足以翻转或污染头条结论）

### D1 · 单轮 completion 上限（已修）
4096 上限下，**7/30 的 D 行被截断，A 零截断**（推理模型把预算烧在 reasoning 上）。
修法：提到 16384。**性质**：单侧截断 → 方向性偏袒 A。

### D2 · 整轮步数上限 `max_turns`（已修，且发现「上限不是中立参数」）
| `max_turns` | A 撞上限 | D 撞上限 | A 工具数 | D 工具数 |
|---|---|---|---|---|
| 8 | 0% | **64%** | 3.04 | 8.12 |
| 20 | 0% | **20%** | 5.24 | 13.04 |
| 40 | **12%** | 8% | **9.96** | 14.92 |

**排除撞上限的行会翻转符号**（全部行 D/A=1.1398「D 更贵」→ 排除后 0.8617「D 更省」）。
**更重要的发现**：抬高上限会**同时改变两臂行为**（A 从 5.24 涨到 9.96），
所以「把上限抬到不构成约束」**在原理上达不到**——预算不是一个中立旋钮。

### D3 · A 臂提示词缺陷（已修）
条件 A 只有 `run_command`，却和 D **共用同一份系统提示**——那份提示要求「用 `read_file` 读文件」
并禁止用 `run_command` 读文件。**对 A 而言自相矛盾**，方向性偏袒 D。
修法：每臂用与自身工具集匹配的提示 + 新增 A′ 臂。**此前所有 D/A 对比都带这个偏袒。**

### D4 · C30：参考客户端吞掉读内容（已修，**影响最大**）
`format_aci_result` 的读投影有 `if len(lines) <= 10`：**窗口超过 10 行就整段丢弃**，
只留 `{ok, content_hash, total_lines}`。而 `file.view` 默认窗口 **80 行**，
工具描述却承诺「a window of lines」。

**实测证据（三方一致）**
- 产品信封**是好的**：`ae` 返回的 `data.lines` 有完整 45 行
- 参考客户端投影只剩 `{ok, content_hash, total_lines}`
- D 侧 live：**180/204 次 `file.view` 只拿到元数据**、**45%（91/204）在重复查看同一路径**、
  绕道 `repo.search`（**301 次 / 65.7k token**）与 shell 读文件

**为什么长期没被发现**：契约检查 `tools/projection_contract.py` 用 **3 行**的 fixture 测
`file.view`，恰好落在 ≤10 的例外分支里，**检查一直是绿的**。

**修法与锁定**：携带工具实际返回的窗口；新增两条 **60 行 + 默认参数**的检查；
**做了负对照**（把旧规则套回去，新检查必须 FAIL——已验证会 FAIL）；C30 设为独立门禁项。

**影响**：修完前后，D 的工具数 **13.05 → 3.63**、观察 token **1316 → 609**、
成功率 **0.7733 → 0.8267**；**结论从「D 更贵」翻成「D 更省」**。

### D5 · C14/C16 门槛未达成（**未修，见 §6 P1**）
见 §4.5。

### D6 · 生成端点不可靠（已缓解，未解决）
- 端点约 **300s 就 502**；超过 300s 的请求必失败
- 服务的都是推理模型，**把输出预算烧在 `reasoning_content`**：一次 180 行请求
  completion 16384 / reasoning 16209 / **content 0 字符**
- 因此**生成不出「大 fixture」**，large tier 改为「小 fixture + 长失败转储」机制
- 空回复必须当成失败（HTTP 200 + content 空），否则整个 job 被静默跳过
- **后果**：30 个生成任务只做出 15 个

### D7 · 生成器顺序错（已修）
测试写在 buggy 模块**之后** → 测试照着错误行为写 → 没有任何正确实现能满足它。
门禁表现为 **A2 GOLDEN 通过 16/31、A3 独立解通过 15/31**。
> **修订注（2026-09-26，TF-0104）**：这两个分母是**第 11 轮那批 32 个候选**的记录，不是当前状态。
> 用当前产物（35 候选，其中 33 个被 A2/A3 评估）重算是 **A2 17/33、A3 15/33**；差 4 个候选 = 3 个本轮新增
> + 1 个当时就缺 `task.json`。原数字保留作留痕，但**引用时必须写明是哪一批**，不能当现值用。
修法：改成 TDD 顺序（正确实现 → 通过它的测试 → 使其失败的 buggy 版）+ **写入前本地自检**。

## 6. 我定位的问题（按严重度排序）

### P1 · C14/C16 的门槛与度量口径不匹配（**需要你决策**）
**问题**：两条声明的门槛是「占读桶总量的百分比」，而这个量**天然随读法混合漂移**——
它不是接口的性质，是「这次任务集恰好读了多少内容」的性质。
**证据**：同一个未改动的投影代码，在 v1.3.0 的读法下是 20.4%，在 v2.0.0 下是 8.3%；
而**混合不变**的事实是「去掉了 45.5% 的信封开销」。
**我为什么没有自己修**：两条路我都刻意没走——
（a）**不擅自挪门槛**（看到数字后改度量 = 事后挑选，正是这套体系要防的）；
（b）**不擅自改成「信封开销口径」**（那是产品决策）。
**需要你决定**：要么修产品让投影在内容主导的读法上也省 ≥10%，要么**显式地**把声明改成
「信封开销削减 ≥40%」并在 `docs/claims-and-evidence.md` 与 `tools/claim_gate.py::THRESHOLDS`
里写明理由。**当前 `claim_gate` 红在这两项上，红得有道理。**

### P2 · 「省 token」的归因是提示词，不是接口（**最重要的结论性问题**）
D/A′ = 1.0567 [0.8435, 1.379]，区间跨 1.0。**接口本身没有可证明的 token 优势。**
D/A = 0.6853 的那 31.5%，在提示词拉平后消失。
**含义**：若对外声称「ACI 省 token」，实际卖的是**提示词工程**。

### P3 · 成功率优势样本不足
+0.12（D−A）、+0.16（D−A′）方向一致且配对胜负比 16:7 / 17:5 看起来有利，
但 **n=75 只够检出 0.1791，预注册 MDE 是 0.15**。差 30 对。
**不能写「成功率更高」**，只能写「未检出」。这是**数据缺口**，加样本可解。

### P4 · 工具调用数没有优势
D/A 工具比 1.0074（点估计已在门槛错误一侧）→ **产品缺口**。
根因（第 11 轮定位）：typed op 粒度更细（读/改/跑各算一次），而裸 shell 一条命令能读+改+跑。
**注意**：这条在修完 C30 后从 2.97 降到 1.0074，说明第 11 轮那个「3 倍」主要是 C30 造成的。

### P5 · 「大观察任务」占比只有 16%，未达预注册的 1/3
准入的 15 个任务里只有 **4 个** pristine 观察 ≥1000 token；占整个 25 任务集的 **16%**。
**含义**：token 类结论仍主要建立在**小观察**上，**构造效度偏弱**。
产物：`eval/task_admissibility.json` 的 `pristine_observation_tokens`。

### P6 · 任务集语言标签不统一（数据质量问题）
`bench/aci/tasks/*.json` 里同一门语言出现两种写法：**`ts: 2` 与 `typescript: 2` 并存**
（另有 `windows: 2` 是任务类别而非语言）。
**影响**：任何按 `lang` 分组的统计都会把 TS 拆成两组。**建议审计者独立核对**。

### P7 · `read_files` 消融显示 D 高度依赖读工具
without 臂（seed 42，隐藏 `read_files`）：

| 臂 | 成功率 | 工具 | token |
|---|---|---|---|
| A | 0.6400 | 4.48 | 993.9 |
| A′ | 0.7600 | 5.24 | 905.3 |
| **D** | **0.3200** | 2.52 | 233.8 |

D 的成功率从 0.83 掉到 0.32。**含义**：D 的价值高度集中在读工具上——
这也解释了为什么 D4（客户端吞掉读内容）能把结论整个掀翻。

> **修订注（2026-09-26，TF-0103）——本条结论已撤回，原因有三**：
> ①**名称写错了**：被隐藏的 `read_files` 是 AE 的 **`file.read_many`（批量读）**，不是「读工具」；
> 单文件读 `read_file` = **`file.view` 仍然可用**，而且消融 D 臂实际用了 **24 次**（10/25 行），
> `file.read_many` 用了 0 次。所以这不是「把读工具拿掉」的实验。
> ②**预算混杂**：消融 D 臂 **13/25 行**是 `completion_truncated_turns=1`、`llm_completion_tokens=16384`、
> **0 次工具调用**，且全部失败（15/17 个 D 失败行都是 `turns=1`）。**剔除这 13 行后 D = 8/12 = 0.6667**，
> 不是 0.32。也就是说 0.32 主要测的是「端点把 completion 预算烧在 reasoning 上」，不是工具依赖。
> ③**同一轮里 A/A′ 的配置没变**（隐藏 `read_files` 对它们无效），但它们的数字也动了
> （同 seed 42：A 0.80→0.64、A′ 0.68→0.76、A′ 观察 token 640→905），说明运行间漂移与臂间差异同量级。
> **处置**：已按 §3.3 用不构成约束的预算重跑 without 臂（`--arms without --seeds 42,43,44 --max-turns 20`）。
> 重跑结果见下方「最终结论」。**在重跑结果出来之前，P7 不得引用。**
>
> **最终结论（2026-09-27，3 seed / 75 配对格，§3.3 两个预算都不构成约束）**：
>
> | | D **with** 批量读 | D **without** | 比 |
> |---|---|---|---|
> | 成功率 | 0.8800 | **0.8800** | **净 0**（仅 with 赢 3 / 仅 without 赢 3；**McNemar 精确 p = 1.0000**） |
> | 工具/轮 | 3.89 | **4.55** | **×1.1678，CI95 [1.0440, 1.2901]（整段 >1.0，可主张）** |
> | 观察 token/轮 | 578.31 | 555.88 | ×0.9612，CI95 [0.8567, 1.0657]（跨 1.0，**无证据**） |
>
> 逐 seed 方向不一致：seed 42 `+0.08`、seed 43 `−0.08`、seed 44 `±0.00`。
> **P7 撤回。** 去掉批量读（`file.read_many`）的**唯一可主张效应是多约 17% 的工具调用**；
> 成功率没有任何可检出的下降；观察 token 无证据。第 12 轮那个 **0.32 是 completion 上限截断造成的假象**
> （13/25 行 `completion_truncated_turns=1` 且 0 次工具调用，剔除后 D = 0.667）。
> **所以「D 高度依赖读工具」不成立**；能说的是「**批量读省下约 17% 的工具调用，但不改变成功率**」。

## 7. 我认为可疑、需要审计者独立验证的点

> 这一节是**主动暴露弱点**。请优先攻击这里。

1. **单模型、单机**。全部 live 结论来自 `sn-glm-5-3-flash` 一台机器。
   **换模型、换端点，结论可能再次改变**（历史已证明：三个测量缺陷轮流改写过头条数字）。
2. **token 是 `len//4` 代理**，实测**低估约 33%**，且形状依赖、**无单一修正系数**。
   所有 token 比值都建立在这个代理上。
3. **`temperature=0` 不代表确定性**：端点接受 `seed` 但不严格复现。3 个 seed 给的是经验区间。
4. **端点行为时变**：同一请求不同时刻成功率不同；生成环节实测「单独探测 5 个模型全成功、
   流水线里连续全失败」。**审计者若复现，请注意时点差异。**
5. **任务集 40% 是 LLM 生成的**（15/25），且生成器与变体模型都来自同一个端点家族。
   独立性声明（`provenance.independent_of`）依赖生成时的提示隔离，**无法从产物事后验证**。
6. **C5（学习成本）只高出门槛 0.014**（0.7143 vs 0.70）——**边际通过，极不稳健**。
7. **跨 shell 的 4 倍差距含进程启动开销**，不代表吞吐/内存/并发；单机单次会话。
8. **门禁的 24 项里，真正测「产品能力」的只有 3 类，不要把 22/24 读成「产品大部分达标」。**
   按 `eval/evidence.json` 的 `mode` 字段：
   - `live_model_probe`：**只有 C5**（学习成本，n=15，且只高出门槛 0.014）
   - `wall_clock`：**只有 C11**（跨 shell 性能，n=5）
   - `deterministic`（对产品投影做固定轨迹复算）：C14、C16
   - 其余 20 项是 `mock` / `cargo_test` / `deterministic` / `statistical_audit` /
     `content_fingerprint` 等**自检**，测的是管线与契约，**不测模型能力**
   - **关键**：**头条 live A/D 对比（C13）根本不在这 24 项里**——它是「记录测量、不设门槛」的声明。
     所以**「门禁绿」≠「产品结论成立」**，两者是两套东西。
9. **`eval/evidence.json` 的 `value` 字段含义不统一**：有的是比值、有的是布尔 1.0、
   有的是比例。**按 value 排序或平均是无意义的。**
10. **历史轮次数字仍留在文档里**（C13 的「第 10/11 轮」行）。它们**已被证伪或取代**，
    但为了留痕没有删除。**审计者若抓到矛盾，请以 §4 为准。**

## 10. 一句话总结（供审计者核对是否与数据一致）

> **跨 shell 性能是真实且巨大的（≥2 倍，5/5 操作）；token 节省是真实的但归因于提示词、
> 且依赖客户端行为（D/A=0.685，D/A′=1.057）；成功率优势方向有利但样本不足（+0.12，需 105 对）；
> 工具调用数没有优势（1.0074）。而最该被审计的是——这套东西的头条数字曾被 **D2 与 D4 两个缺陷各自单独翻转**过，
> 另有三处缺陷（D1–D3）造成**方向性偏袒**，所以任何单轮结论都不该当成定论。**
