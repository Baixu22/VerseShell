# 第 14 轮 live：结果、行处置与两条结构性问题（task set v3.0.0）

> 本轮是第一次在**样本量达标**、且**预先写死了行处置规则（§0.6）**的条件下跑的 live。
> 它的头条结论是：**在预注册规则下，本轮没有一条成功率或 token 比值对比可主张**——不是因为效应小，
> 而是因为 D 臂有 14.3% 的格撞上了 completion 预算上限。

## 2. 头条结果（with 臂）

### 2.1 按 §0.6 行处置规则的两个口径

| 臂 | n | `endpoint_failure` | `cap_truncated` | 排除率 | 全量成功率（ITT） | `analysable` 成功率 |
|---|---|---|---|---|---|---|
| A `raw_shell` | 105 | 3 | 2 | **4.8%** | 0.9048 | 0.9400 |
| A′ `raw_shell_coached` | 105 | 0 | 0 | **0.0%** | 0.8762 | 0.8762 |
| **D `verseshell_aci`** | 105 | 0 | **15** | **14.3%** | 0.8381 | **0.9556** |

**判定：两条成功率对比都不可主张**。`verseshell_aci_vs_raw_shell` 与
`verseshell_aci_vs_raw_shell_coached` 均被 §0.6.3 阻断，原因是
`exclusion_rate_above_10pct` + `analysable_and_itt_disagree_in_sign`（前者另有 `api_error_rows_present`）。

### 2.2 数字本身

| 量 | 点估计 | CI95（按任务聚类） |
|---|---|---|
| 成功率 D−A（配对 McNemar） | **−0.0667** | **[−0.1331, −0.0003]** |
| 成功率 D−A′ | −0.0381 | — |
| 观察 token 比 D/A（`len//4` 代理） | 0.6347 | [0.5148, 0.7776] |

McNemar：仅 A 赢 **10** 格、仅 D 赢 **3** 格，精确 p = 0.0923。

**必须一起读的三件事**：
1. **全量口径下 D 的成功率显著更低**（区间不含 0），而**剔除截断行后 D 更高**（0.9556 vs 0.9400）。
   符号被纯机械的预算截断翻转——这正是 §0.5/§0.6 存在的原因。
2. **真实 tokenizer 口径下 D 的总开销更高**（1.3583，整段区间在 1.0 之上），与第 13 轮方向一致。
3. **CPST 看起来省（0.6852），但非劣不成立**，所以「省 token」不能主张——否则就是奖励失败。

## 3. 两条结构性问题（已登记为节点）

### 3.1 D 臂专属的 turn-1 completion 截断（TF-0121）

15 行 D 侧截断的字段签名完全一致：`completion_truncated_turns=1`、
`llm_completion_tokens=16384`（撞满）、`tool_calls=0`、`observation_tokens=0`、
`trajectory` 为空、`elapsed_ms≈200000–213000`、`last_error=None`、`harness_crash=False`。
即模型把整轮预算烧在 reasoning 上，**从未发出工具调用**。

**归因（原假设「large tier 任务导致」被证伪）**：逐臂均值 —— 每行输入提示 token
A **9,015** / A′ **9,924** / **D 11,393**；每行 completion token A 1,593 / A′ 1,610 / **D 3,017**。
被截断的 12 个任务的 pristine 观察量跨度是 **141–1559 token**（含多个 small/medium），
**与任务规模无关**。所以成因是 **D 条件本身的提示体积与推理量**。

### 3.2 与端点 300 秒上限结构性不兼容的格（TF-0122）

`python_csvlite_parse_80d158b2` 的 A 臂格**连续 6 次补跑全部 HTTP 502「非流式响应超时(300秒)」**，
而同一个任务在 without 臂第一次补跑就成功（返回普通 FAIL 行）——失败是**任务/条件特异**，
不是端点整体不可用。该格使 `merge_live_runs.py` 拒绝合并整个 with 臂。

**处置**：用工具自带的 `--allow-api-errors` 合并并把产物标为 partial
（`live_config.api_error_rows = 3`），**不绕过任何门槛**——§0.6.3 第 3 条仍使含 `api_error` 的对比不可主张。
旧基线备份在 `audit-r12-scratch/latest_live_round13_backup.json`。
without 臂的三行补跑成功，因此对照臂是**干净的**（`api_error_rows = 0`）。

> 这条暴露的管道缺陷：一个格的端点失败会让**整轮** live 无法合并、全部派生产物永久陈旧。
> §0.6 早已把 `endpoint_failure` 定义为一等行类，但合并脚本仍按「任一行 api_error 即拒绝」处理。

## 5.5 跑间方差：同配置三个 seed 的符号会翻转（`eval/run_variance.json`，TF-0112）

已发布的区间是**按任务聚类**的 bootstrap，它只建模「抽到了哪些任务」，**不建模跑间方差**。
本轮恰好有**同一配置的三次运行**（同任务集、同模型、同提示、同预算，仅 seed 不同），所以可以直接量它。

| 指标 | seed42 | seed43 | seed44 | 跑间 sd | 跑间 SE / 已发布半宽 |
|---|---|---|---|---|---|
| 观察 token 比 D/A | 0.7182 | 0.6220 | 0.5817 | 0.0701 | **0.31×** |
| 工具调用比 D/A | 0.8831 | 0.7829 | 0.7415 | 0.0728 | — |
| **成功率差 D−A** | **+0.0286** | **−0.0857** | **−0.1429** | 0.0873 | **0.76×** |

**必须一起说的两点**：

1. **成功率差的符号在 seed 之间翻转**：seed42 说 D 更好，seed43/44 说 D 更差。已发布的配对 CI95
   `[−0.1331, −0.0003]` 确实不含 0，但**它只覆盖任务抽样**——把这三次运行当成重复后，
   「D 显著更差」这个读法**不稳健**。
2. **观察 token 比的跑间跨度是 0.137（约 21% 相对）**，而第 13 轮那条头条主张的余量只有 0.0212。
   也就是说：**单轮的点估计在跑间方差面前是脆弱的**，这与第 12↔13 轮之间测到的 0.2577 漂移一致。

**限制（写在产物里，不隐藏）**：三个 seed 给出的是 **2 个自由度**的标准差，所以这是问题的
**下界**而非标定过的方差成分——它能证明「已发布区间偏窄」，**不能**给出应当替代它的区间。
成熟做法是每配置 ≥3 次完整重跑并做方差成分模型（TF-0112 的验收项）。

## 6. 这一轮该怎么被引用
- ✅「第 14 轮在 105 对上跑完，**预注册规则判定两条成功率对比都不可主张**，因为 D 臂排除率 14.3% > 10%。」
- ✅「全量口径下 D 的成功率 CI95 为 [−0.1331, −0.0003]；剔除截断行后符号相反。」——**两个口径必须一起给**。
- ✅「真实 tokenizer 口径下 D 的总 token 比 1.3583 [1.0303, 1.8986]。」
- ❌「D 成功率更低」——单口径引用，违反 §0.6.2。
- ❌「ACI 省 36.5% 观察 token」——该对比被 §0.6.3 阻断。
- ❌「CPST 省 31.5%」——非劣不成立。
- ❌ 跨任务集版本与第 12/13 轮直接比成功率（谓词与任务集都变了）。
- ❌ 把 `[−0.1331, −0.0003]` 读成「D 显著更差」——该区间只覆盖任务抽样，而**同配置三个 seed 的成功率差符号会翻转**
  （+0.029 / −0.086 / −0.143，见 §5.5）。引用时必须同时给出这条跑间方差。
