# 现有采集数据分析：可保留的结论、短板与缺口

分析日期：2026-10-01。本次仅本地读数据、重放服务和临时副本上的评分验证，**没有模型端点调用**。

## 1. 判断

现有数据可用，不能等同于完整正式验收。C16 的局部读取压缩在这批真实调用上达到
原门槛，应停止继续追求压缩比例；下一步重点应转为评分可靠性、故障处理和累计输入开销。

| 问题 | 本次证据 | 判断 |
|---|---|---|
| C16 读取观察压缩 | 124 个可复现调用，71699 → 62936 观察代理 token，节省 **12.22% ≥10%** | 局部机制达到原门槛，保留实现；没有宣告整个证据链通过 |
| C14 摘要缩短 | 同一集合，65917 → 62936，**4.52% <15%** | 保留 FAIL，不削减正文或摘要安全性追绿 |
| ACI 累计 usage | with 配置严格有效配对：D/A **1.376**，D/A′ **1.694** | 当前可分析样本里输入开销明显偏高，不能声称整体省 token |
| 任务评分 | 两个任务各有正确实现被拒绝、错误实现被接受的本地反例 | 已证实工程缺陷，优先修新版本评分；不篡改已采原始成绩 |
| 端点与采集 | 68 个端点失败、83 格未完成；状态文件与进程实际状态不一致 | 需要可靠的暂停、恢复和状态记录，不需要承诺端点永不失败 |

| 分片 | 已采/计划 |
|---|---:|
| with 42 / 43 / 44 | 105 / 105，各分片完整 |
| without 42 / 43 | 105 / 105，各分片完整 |
| without 44 | 22 / 105 |
| 合计 | **547 / 630** |

完成以下核验：每分片配置与源代码/二进制指纹一致；格身份无重复、无越界；83 个缺格
逐项列出；with 合并的 315 行与 checkpoint 按既定行策转换后逐字段一致。所有分析输入
保存 SHA-256，分析前后验证未改动。不同配置之间只有预期的 read_files 隐藏选项不同。

437 格原始成功、42 格非端点失败、68 格端点失败。端点失败应按未知结局处理，不能当作
能力失败。without 第三个分片停在任务清单前部，缺失任务并非随机抽样。

## 3. 端点问题有集中爆发，不能靠删除错误行消除偏差

| HTTP 状态 | 格数 | 记录原因 |
|---|---:|---|
| 401 | 41 | 代理上游账号缺少 accessToken |
| 402 | 12 | 上游积分不足 |
| 502 | 15 | 包含 300 秒非流式响应超时及其他上游错误 |

401 为跨分片的 **41 格连续错误段**，随后有 **12 格连续 402**。这说明本轮缺少
认证/额度错误后的停发保护；仅“不重试当前失败格”不能阻止把后续任务逐个送进同一故障。
全批端点失败率为 **68/547=12.43%**，但不同条件、阶段的缺失率不同，不能只用总比例判断偏差。

68 格中 9 格记录了错误发生前的成功请求 usage，共 7418 token；失败请求本身的 usage 未返回。
其余记录为零也不证明免费。因此不能从这些日志得到全批完整计费量，更不能计算完整金额成本。

最后 checkpoint 写入于 **10-01 01:10**。检查时 supervisor/采集进程均不在，状态文件
仍保留前晚的 running。**终止原因未查明**，不能断言是认证错误导致进程退出，也不能把
陈旧状态解释为仍在正常运行。需要 heartbeat、格开始/结束记录及重启后的状态核对。

## 4. C14/C16：从完整 with 配置提取真实读取重放

输入为独立集合中的 315 行 with 产物，不是旧 r15 基线，也未覆盖正式 eval 文件。
126 个已发生读取中，124 个复现了原记录的观察 token 数，覆盖率 **98.41%**；两个排除
都是运行中生成的 `out/result.txt`，原始 fixture 无法还原。

| 指标 | 旧渲染/完整摘要 | 当前渲染/短摘要 | 节省 |
|---|---:|---:|---:|
| C16，观察 `len(text)//4` 代理 | 71699 | 62936 | **12.22%** |
| C14，原摘要差值口径 | 65917 | 62936 | **4.52%** |
| C14，未截断的 106 调用 | 46607 | 44124 | **5.33%** |

C16 分操作：77 个 file.read_many 节省约 13.0%，47 个 file.view 节省约 10.3%。
重放报告中的正文计量均为 223897 字符；本次结果延续已有无损投影契约。

两条指标是不同反事实，**不能相加**。这不是模型 tokenizer 或总 usage 节省，也不是
证明未发生的读取会同样受益。匹配依据仍是 token 数复现，尚缺原始观察文本的逐字节
哈希；生成文件的读取也无法重建。应补足观察留存，而非伪造更高覆盖率。

原 claim 函数对本次离线产物给出 C14=false、C16=true。因全批不完整、端点缺失且
正式 C12 链未刷新，整体 formal_acceptance 仍为 false。可以陈述上述局部机制结果。

## 5. 有效配对：观察更短，不等于累计输入更低

相同配对集合，usage 与逐轮记录求和一致。

下表区间为 **按任务整组重抽 10000 次的探索性 95% 区间**。它不校正信息性缺失、

## 6. 成功率的缺失敏感性

with 严格配对中：A/D 成功数为 **82/85（91 对）**，A′/D 为 **84/86（92 对）**。
这些是冻结评分下的条件样本数，不代表未采或端点失败格的结果。

对每条件原计划的 105 格，将未知分别置为最不利/最有利结局，可得到 D 成功率差范围：

| 处理未知的口径 | D−A | D−A′ |
|---|---:|---:|
| 仅端点未知 | −5.71～+14.29 个百分点 | −6.67～+12.38 个百分点 |
| 同时将预算排除视为未知 | **−7.62～+16.19 个百分点** | **−8.57～+13.33 个百分点** |

范围跨零，因此“成功率更高”的方向不稳健。该范围是样本中的未知结局界，**不是置信区间**，
没有包含抽样不确定性。without 再叠加未采格后界限更宽，不能支持总体能力提升结论。
个别条件样本中所有配对成绩一致会得到退化 bootstrap 区间，不能据此证明总体完全等效。

本批 0 个 completion 截断；原行策标记 10 个 turns≥8 的格，其中 8 格原评分成功。
不要现在改预算或事后移除行策；下一版应记录明确终止原因，区分恰好在最后一轮完成和真正耗尽轮数。

## 7. 评分短板已用双向负对照证实

42 个非端点失败中，**30 个（71.4%）集中在两个任务，各 15 个**：

- rust_add_unit_test 要求出现特定 `assert_eq!(add(1, 2), 3)`，但任务只要求增加测试。
- rust_search_and_edit 要求出现 `return a + b`，但合法 Rust 尾表达式 `a + b` 同样正确。

在临时副本中执行四个控制，未修改冻结任务或原始成绩：

| 控制 | 冻结评分 | cargo test --offline | 结论 |
|---|---|---:|---|
| add：有效的其他输入测试 | FAIL | exit 0 | 假阴性 |
| add：注释带指定字符串，函数实际乘法 | PASS | exit 101 | 假阳性 |
| sum：正确尾表达式 | FAIL | exit 0 | 假阴性 |
| sum：注释带指定字符串，函数实际减法 | PASS | exit 101 | 假阳性 |

这证明评分规则有缺陷，**不等于已经证明全部 30 条历史输出都正确**，也不把它们直接改成 PASS。
35 任务中 9 个必需判据不包含执行验证，其中有些是合理的文件产物检查，须逐项评估；
不能笼统判全部无效。两个已证实缺陷优先修到新数据集版本。runner 明确不执行 optional_verify，
需要行为正确性的任务必须把必要测试放进 required success。

## 8. 其余工程缺口

- with 中 file.replace_exact 失败 **6/90**；without 为 **6/65**。同一轨迹中共 10 次
  出现失败替换后转向 file.write。缺少错误代码和完整观察，尚不能确定是定位、摘要还是
 其他参数问题；不能据此删除乐观并发校验，应补可诊断字段。
- with 中实际使用 read_many 77 次；without 主要为 137 次 file.view。配对与时间不一致，
  不能仅靠这两个总数决定删除批量读取。
- 401/402 连续失败仍继续调度、进程消失后 running 不更新、最后在途格无法定位结束状态，
  是比进一步压缩观察更优先的采集可靠性问题。
- C12 是来源新鲜度门禁，不代表逐轮协议适配、评分效度和服务可靠性都正确；各项证据需要分开。
