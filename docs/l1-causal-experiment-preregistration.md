## 1. 背景与待检验的观察（不是已证原因）

P0-1 的离线复算（来源：`docs/repair-live-closure-handoff-2026-09-29.md` §4 与
`bench/aci/results/latest_live.json`，该产物 `generated_at=2026-09-28T22:41:52Z`，
`max_turns=20`、`max_tokens=16384`，A/A′/D 各 105 格）：

| 观察 | 数值 | 口径说明 |
|---|---:|---|
| D 有 completion 截断的格子 | 15/105 | `completion_truncated_turns > 0` |
| 其中首轮截断且首轮零工具调用 | 9 | 该 9 格首轮 `llm_completion_tokens=16384`，耗时约 187.8s–215.6s |
| 其中后续轮截断 | 6 | 现有产物无逐轮字段，只能由行级总量间接推断 |
| 15 格中最终成功 | 2 | **截断 ≠ 失败**，成功不能当作截断的代理 |
| A 有 completion 截断的格子 | 3/105 | `completion_truncated_turns > 0` |
| A 被统一 row_policy 计为 `cap_truncated` | 4/105 | 第 4 格来自 `turns >= max_turns(20)`，与 completion 截断是**不同字段**，不可互换、不可相加 |

交接单给出的口径是「15/105 D 格把 16384 预算烧在首轮且零工具调用；其中 9 格首轮完全零工具」。
本文保留这两个原始数字，同时明确指出：**现有产物没有逐轮记录**，因此从产物本身无法证实或证伪
「15 格全部是首轮」，只能确认 15 格有截断、9 格是首轮零工具。这个洞正是逐轮记录要补的，
而 `tools/live_turn_diagnostics.py` 对旧产物一律报 `unknown_field_missing`，不猜。

**本实验要做的不是"证明截断是长度造成的"，而是把两个互相纠缠的解释分开测：**
提示词/工具 schema 的**体积**，与接口**框架**本身。旧产物里 D 的提示体积与框架同时不同，
且后续轮输入体积由模型自身动作决定，任何相关性都不足以归因。

## 2. 假说与可证伪条件

- **H-length（长度假说）**：提示词 + 工具 schema 的静态体积本身驱动首轮 completion 截断。
  - 可证伪：在**同一框架内**只改变静态前缀长度、其余全部不变时，首轮截断率没有可检出的上升
    （判定见 §9）。
- **H-framework（框架假说）**：接口框架（工具集形状、命名信封、系统提示结构）在长度之外
  独立影响首轮截断。
  - 可证伪：在**长度匹配**的两个臂之间，首轮截断率差没有可检出差异。
- 两个假说可以同时成立（长度是原因之一，框架在长度之外仍有效），也可以都不成立；设计必须能区分
  四种模式（§9 判定表）。框架内部究竟是哪个部件起作用（工具数量、schema 形状、typed op 命名、
  系统提示措辞）**本实验不能识别**，不得在结论里细分到部件。
- 需要显式排除或承认的竞争解释：任务形态/难度、端点当时状态与时延、代理的 300s 非流式超时
  （会把长 completion 变成 `api_error` 而不是 `length`）、`temperature=0` 也不保证的采样随机性、
  多轮累计历史体积的不可控。

## 3. 实验臂与对照结构

| 臂 | 框架 | 静态前缀长度 | 构造 | 作用 |
|---|---|---|---|---|
| **A0** | A（raw_shell：单 `run_command` + shell 提示） | 原生短 | 现有 `--conditions raw_shell` | 描述性重现旧 A 基线 |
| **D0** | D（ACI 工具集 + `shell_neutral` 提示） | 原生长 | 现有 `--conditions verseshell_aci` | 描述性重现旧 D 基线 |
| **D-L** | D **不变**（工具名、schema 语义、权限、消息组装全部不变） | 缩短到与 A0 匹配 | 仅删除系统提示中**非操作性**的模板句与重复内容，逐字保留删除前后的文本并写入 study manifest | H-length 在框架 D 内的对照 |
| **A-F** | A **不变**（单工具、权限不变） | 拉长到与 D-L 匹配 | 在 A 系统提示尾部追加**冻结的中性填充块**（与任务无关、不含任何解法信息、逐字公开、字符数与 D-L 的删减量相等） | 长度匹配下的框架-only 对照 |

主对照（配对）：

| 编号 | 对照 | 变化量 | 不变量 | 检验 |
|---|---|---|---|---|
| **C1** | A-F vs D-L | 框架 | 静态前缀长度匹配 | H-framework |
| **C2** | A0 vs A-F | 长度（同一中性块，同 Δ） | 框架 A | H-length |
| **C3** | D0 vs D-L | 长度（同一删减量，同 Δ） | 框架 D | H-length（重复） |
| **C4** | A0 vs D0 | 长度 + 框架同时变 | 无 | **仅描述性**，不用于因果推断 |

补充臂（预算允许时执行，非主对照）：把同一中性填充块按相同 Δ 分别追加到 A0 与 D0（A-F2、D-L2
的**上向**版本），用于检查"填充本身是否惰性"。若因预算不执行，结果里必须写明未做该检查。

**已知混淆，必须披露**：删减 D 的提示文字可能改变模型行为，追加填充也可能带语义。
「长度」操纵与「语义」不可能完全分离。因此 C2/C3 只有在填充/删减文本被逐字公开、且
A-F2/D-L2 惰性检查（若执行）未显示反常时才解释为长度效应；否则只能报告"提示文本变化"。

每臂保持：同一任务集与 fixture、同一成功谓词、同一 `max_turns`、同一 `max_tokens`、同一
`temperature`、同一 seed 集合、同一超时与重试规则、同一代码与观测面指纹。

## 4. 长度匹配口径：字符，不是 token

- **匹配量 = 静态前缀（系统提示 + 工具 schema 的 JSON 序列化）的 UTF-8 字符数。**
- 为什么不用 token：端点返回的 `llm_prompt_tokens` 是**每次请求的输入 usage 累计**（含提示、
  schema 与重发历史），不是单次前缀体积；本仓库的 `len//4` 是观察文本代理（P2-5 已认定
  它既会低估也会高估），`cl100k_base` 也不是被测模型的分词器。字符数在冻结时可精确、
  可复现、可逐字披露，是唯一能在**看结果之前**固定的口径。
- 为什么不能只按 token 匹配：要在计划阶段做到 token 精确等长必须先调用端点分词器（当前不可得），
  而反复调用来回凑长度会引入新的端点噪声与选择性。
- 因此采用 **字符匹配 + 后验操纵检查**：预先声明容差——每个对照对内，两臂首轮 `prompt_tokens`
  的**中位数相对差必须 ≤15%**，且方向与设计一致（A-F ≥ A0，D-L ≤ D0）。超容差的格子标记
  `matching_failed`，从确认性对照中排除并单独列出；含全部格的分析作为敏感性分析同时报告。
- 逐轮 `prompt_tokens` / `completion_tokens` 由 `turn_diagnostics` 记录，把"长度"从宣称变成
  可核对的观测量。

## 6. 逐轮结局与格级结局

**逐轮（每条 `turn_diagnostics` 记录）**：

- `finish_reason`（尤其 `length`）
- 该轮 `prompt_tokens` / `completion_tokens`
- `reasoning_returned` / `reasoning_chars`（**仅在端点返回时**；缺失记入 `fields_missing`）
- `tool_call_count`
- `request_ms`
- `content_chars`

**格级主要结局（二值）**：`turn1_truncated_zero_tool` = 首轮 `finish_reason=="length"` 且
首轮 `tool_call_count==0`。

**次要结局**：`completion_truncated_turns`、`turns`、`tool_calls`、`success`（实际谓词）、
`llm_prompt_tokens`/`llm_completion_tokens` 合计、`api_error`、逐轮 `request_error`、`elapsed_ms`。

**诊断结局（不作为主张）**：`tools/live_turn_diagnostics.py` 的分类计数
（`reasoning_burn`、`budget_burn_without_reasoning_evidence`、`truncated_other_turn`、
`no_truncation`、`unknown_field_missing`、`unknown_incomplete_turn`）。

口径纪律：`completion_truncated_turns` 与统一 row_policy 的 `cap_truncated`
（= `completion_truncated_turns>0` **或** `turns>=max_turns`）不是同一个量，任何计数都必须写清
用的是哪一个分母；A 的 3 与 4 就是这两个口径，不能互换。

## 7. 样本量、重复与执行顺序

**第一阶段：可行性探针（不是确认性数据）**

- 规模：12 格 = 离线复算确认的 9 个"首轮零工具截断"格 + 3 个同任务的非截断格，覆盖各臂各 1 次。
- 目的：确认端点能力、确认 `turn_diagnostics` 真的被写入且端点是否返回 reasoning 字段、
  确认代理 300s 行为、确认臂的构造（删减/填充文本）可行。
- **不进入确认性检验**；其结果不得用于挑选臂、任务或长度目标；若探针要求改协议，必须重写本预注册。

**第二阶段：确认性采集（测试方执行）**

- 网格：35 任务 × 3 seed = 105 格/臂 × 4 臂 = 420 格/重复；**完整重复 3 次** → 1260 格。
  与现有 105 格/条件的规模一致，便于对照。若要缩减任务集，缩减规则必须在第一格之前写死，
  不能按结果挑任务。
- 重复的用途：把 run 作为聚类单位，以及检查方向复现（§9）；**不是**把 3 次当 3 倍 iid 样本量。
- 判定阈值：105 对配对格下，精确 McNemar（双侧 α=0.05）在单向不一致对 ≥6 时即拒绝
  （2×0.5⁶=0.031），即最小可检出的不一致比例约 6/105≈5.7%。这是阈值，不是功效保证；
  若不一致对方向不单向，所需对数更高，因此把"≥2/3 重复方向一致"作为主张前提。
- **平衡顺序（必须）**：block = 任务 × seed；block 内 4 臂按冻结的轮转顺序执行
  （第 2、3 次重复使用逆序/平移），使每臂在每个位置上出现次数尽量相等；记录每格开始/结束时间、
  相邻格身份与端点错误。**禁止"先跑完一个臂再跑另一个"**。
- 端点漂移检查：若同一重复内 A0 的首轮截断率与其他重复相差 ≥10 个百分点，该重复标记为
  `endpoint_drift_suspect`，只做描述性报告，不进入确认性合并。

## 8. 停止与重试规则（预先声明）

- `finish_reason=="length"` 是**结局，不是重试触发**。不得"重跑到成功"或"重跑到不截断"。
- HTTP 429/5xx/连接错误/代理 300s 超时：每格最多 3 次尝试，指数退避（2s、4s）；每次尝试都保留在
  checkpoint（`turn_diagnostics` 会记录 `request_error`）。3 次后该格记 `api_error`，按事前规则
  排除出主要分析并计入排除比例；**代理 300s 超时不得记作任务失败**。
- 真实模型解题失败照实保留，不重试到成功。
- 若某个 block 的 `api_error` 比例 >50%，暂停整轮并报告；是否重启由测试方按本规则决定，
  重启必须整轮进行，不拼接部分结果。
- 禁止基于效果大小的提前停止（no optional stopping）；只有端点/安全原因可以中止。
- 端点/模型/proxy 配置发生任何变更 → 停止并按 §11 处理。

## 9. 预先声明的分析

- **单位与配对**：格 = (task, seed, run)。配对对：C1=(A-F, D-L)、C2=(A0, A-F)、C3=(D0, D-L)，
  在同一 task×seed×run 内配对。
- **主检验**：格级 `turn1_truncated_zero_tool` 用精确 McNemar（双侧）；C1/C2/C3 三个确认性对照
  做 Holm 校正（族内 α=0.05）。
- **区间**：每臂报 Wilson 区间（非配对，描述性）；配对差报按任务聚类的 bootstrap 区间
  （重抽任务）。run 维度的变异性单独作为诊断报告，不与任务聚类区间相加。
- **操纵检查（先于结果解释）**：各对照对的首轮 `prompt_tokens` 中位数相对差 ≤15% 且方向正确；
  不成立的对照对标记 `matching_failed`，从确认性分析中排除并单独报告，含全部格的主分析作为
  敏感性分析同时给出。
- **判定表（提前写死）**：

| 模式 | 判据 | 后续动作 |
|---|---|---|
| 仅长度 | C2 或 C3 显著且方向为长度增加→截断上升（≥2/3 重复一致），C1 不显著 | 优先做提示/schema 体积削减，仍须预注册模型可见变更 |
| 仅框架 | C1 显著且 D-L 更高（≥2/3 重复一致），C2 与 C3 都不显著 | 改框架，但必须先预注册模型可见变更与本地验收 |
| 两者都有 | C1 显著，且 C2 或 C3 显著 | 先做低风险长度削减，再做框架实验；分两步报告 |
| 都不是 | C1/C2/C3 全部不显著，且方向差都在最小可检出量级（≈5.7%）以内 | 不是接口体积问题；转向端点/reasoning 预算与任务形态，**不得据此直接改产品** |

- **H-length 被证伪的条件**：C2 与 C3 都不显著，且两对的方向差都不超过最小可检出量级。
- **H-framework 被证伪的条件**：C1 不显著，且方向差不超过最小可检出量级。
- **次要分析**（探索性，不作主张）：逐轮 completion token 分布、reasoning 出现率、
  `truncated_other_turn` 计数、success（保守 ITT 与可分析集两种口径，C14/C16 阈值不变）、
  `api_error` 比例。
- **与旧数字的关系**：不得把 L1 实验格与旧 `latest_live.json` 的行直接合并比较；旧数字只作
  描述性上下文。任何截断率比较必须在同一次采集、同一配置内进行。
- **多重比较**：只对 C1/C2/C3 做 Holm；其余全部标注为探索性。

## 11. P0-3：端点/proxy 变更必须重测，不得继承旧结论

- 当前 300s 非流式响应超时是**已记录的约束**：把 cap 提到 32768 时，同一批格子会以
  `HTTP 502 非流式响应超时(300秒)` 失败（来源：`audit-r12-scratch/cap_probe/results.jsonl` 与
  `audit-r12-scratch/cap_probe_summary.py`）。因此本端点上"提高 cap 再重跑"不是可用方案，
  §5 的 `max_tokens=16384` 是按此约束固定的。
